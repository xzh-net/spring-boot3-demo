# 详细设计

系统内部实现细节——**各环节怎么工作、关键类在哪**。高层架构见 [概要设计](./概要设计.md)。

## 一、安全链（3 条 FilterChain）

| Order | Bean / 类 | `securityMatcher` | 职责 |
|---|---|---|---|
| 1 | `AuthorizationServerConfig.authorizationServerSecurityFilterChain` | `/oauth2/**`、`/login*`、`/consent`、`/logout`、`/.well-known/openid-configuration`、`/.well-known/oauth-authorization-server` | 协议端点 + 表单登录 + **签发准入过滤器** |
| 2 | `AuthorizationServerConfig.deviceVerificationSecurityFilterChain` | `/activate`、`/device-login` | 设备码激活，独立会话上下文 |
| 3 | `ResourceServerConfig.securityFilterChain` | `/api/**` | `/api/permitall/**` → `permitAll`；其余 → `anyRequest().access(endpointAdmissionManager)` |

### 1.1 Order(1) 关键装配

```text
authorizationServerSettings
  ├ issuer                    http://localhost:9000
  ├ authorizationEndpoint     /oauth2/authorize
  ├ tokenEndpoint             /oauth2/token
  ├ deviceAuthorization       /oauth2/device_authorization
  ├ deviceVerification        /oauth2/device/verify
  ├ oidcUserInfo              /userinfo          (未入链，由 UserInfoController 自鉴权)
  ├ clientRegistration        /oauth2/connect/register
  └ oidcLogout                /oidc/logout       (避开 /logout，后者由 LogoutController 处理)
tokenEndpoint providers:
  ├ PasswordGrantAuthenticationProvider   (自定义密码模式)
  ├ DeviceCodeGrantAuthenticationProvider (自定义设备码)
  └ SAS 默认 授权码 / 刷新 提供者（无策略包装，准入已移至签发过滤器）
过滤器（按序）:
  SessionExpirationFilter          → SecurityContextHolderFilter 之后
  ActiveClientTrackingFilter       → 解析 Bearer 写入 Session（多客户端会话隔离）
  AuthorizeIssuanceFilter          → 发码前签发准入（混合登录隔离）
```

> `/userinfo` **不入链**的原因：交给自定义 `UserInfoController` 走本地 Redis 内省，
> 避免 `OidcUserInfoFilter` 抢占并引入 `introspection-uri` 的 HTTP 自回环依赖。

### 1.2 Order(3) 资源链

```java
http.securityMatcher("/api/**")
    .requestMatchers("/api/permitall/**").permitAll()
    .anyRequest().access(endpointAdmissionManager);
```

## 二、双 SecurityContext 与部分登出

```text
CompositeSecurityContextRepository
  loadContext: 先 DEVICE_SECURITY_CONTEXT → 再 OAUTH2_SECURITY_CONTEXT
  saveContext: OAuth2 链 (Order 1) 接管 formLogin，写 OAUTH2_SECURITY_CONTEXT
  containsContext: 任一存在即 true
```

- 设备激活（Order 2）与浏览器 SSO（Order 1）共用同一 `JSESSIONID`，靠**不同 session 属性 key 隔离**
- `AuthorizationServerConfig.partialLogout(...)`: 按 key 只清对应链路的登录态，全部清空才 `session.invalidate()`
  → 登出设备不会把浏览器 SSO 一起踢掉

## 三、认证流程

### 3.1 授权码（管理后台 / 门户）

```text
浏览器 → BFF(:8085) 302 → 9000 /oauth2/authorize
  ① AuthorizeIssuanceFilter: allowLogin(client_id, user_code)?
       scopeCodes 展开为 0 (纯 OIDC 客户端) → 放行
       否则 userCodes ∩ scopeCodes == ∅ → 302 /login.html?error=access_denied
  ② 未登录 → 302 /login → POST /login (BCrypt 校验, principal = user_code)
  ③ 发授权码 → 302 回 BFF redirect_uri?code=...
  ④ BFF POST /oauth2/token (client_secret_basic) 换 access_token + id_token
```

**登录用户详情**：`PlatformUserDetailsService`（唯一 IdP）
- `loadUserByUsername` / `loadUserByUserCode` → `sys_user` 查凭据，principal name = `user_code`
- 角色由 `PermissionService.findRoleCodes(userCode)` 同库供给（`sys_user_role → sys_role`）
- 角色查询异常 → **降级空角色**（fail-closed，无标签猜测）
- `PlatformDaoProvider` = `DaoAuthenticationProvider` 包它，授权链与设备链共用

### 3.2 密码模式 / 设备码

- `PasswordGrantAuthenticationProvider`：用户详情 + `PasswordEncoder` 校验后签发
- `DeviceCodeGrantAuthenticationProvider`：轮询态校验，用户确认后按 `user_code` 反查（`loadUserByUserCode`）

## 四、令牌体系

### 4.1 签发

```text
OAuth2TokenGenerator = DelegatingOAuth2TokenGenerator(
    OAuth2AccessTokenGenerator  ← Opaque (REFERENCE) 强制
    JwtGenerator                ← ID Token (RS256, 含 roles / preferred_username)
    OAuth2RefreshTokenGenerator)
```
- Access Token：`accessTokenFormat` 被 `ClientService` 固定写 `REFERENCE`，**不可改为 JWT**（改了会破坏 Redis 内省）
- ID Token claims：`roles`（业务角色）、`preferred_username`（真实用户名，按 `user_code` 反查）、`aud` = client_id

### 4.2 自省（同进程）

```text
RbacAuthoritiesOpaqueTokenIntrospector.introspect(token)
  ├ RedisOpaqueTokenIntrospector（委托）: Redis 查 oauth2_authorization_record → 令牌有效性/属性
  ├ 主判定基于 grant_type 与 client_id，而非「查不到用户」反推
  └ 叠加业务 authorities:
       roleCodes  = sub → sys_user_role → sys_role
       userCodes  = sub → ... → sys_role_permission → sys_permission(启用)
       scopeCodes = client_id → registered_client.scopes → sys_scope(启用) → sys_scope_permission → sys_permission(启用)
       注入 = roleCodes + (userCodes ∩ scopeCodes)     ← fail-closed
  → 返回 EnrichedPrincipal（保留原 attributes，覆写 authorities）
```

**关键类**：
| 类 | 作用 |
|---|---|
| `RbacAuthoritiesOpaqueTokenIntrospector` | 双维交集注入（自省层） |
| `RedisOpaqueTokenIntrospector` | Redis 令牌校验委托，无 HTTP 自回环 |
| `ScopeService` | scope → 权限码展开（`resolveClientBusinessCodes`） |
| `PermissionService` | 角色码 / 权限码查询（同库联表） |

### 4.3 Redis key 设计

| key 模式 | 内容 | TTL |
|---|---|---|
| `oauth2:authorization:*` | 授权记录（令牌校验依据） | 随令牌有效期 |
| `sessionreg:session:{sessionId}` | 会话 hash：principalName / authorities / lastRequest | 会话期 |
| `sessionreg:principal:{userCode}` | 用户 → sessionId 反向索引 | 会话期 |
| `oauth2:client:id:{id}` | 客户端配置缓存（JDBC+Redis 双层） | **1 小时** |
| `oauth2:client:cid:{clientId}` | 同上（按 clientId） | 1 小时 |

> ⚠️ **双层缓存失效规则**：经 `ClientService.save()` 走 API 写会自动 `refreshCache`；
> **绕过 API 的 SQL 直改不会失效**，必须手动 `DEL` 对应 `oauth2:client:*`，否则自省读到旧 `scopes`/`secret`。

### 4.4 撤销

删 `oauth2:authorization:*` 对应 key → 内省 `active=false`。无需 JWT 黑名单。

## 五、准入裁决实现

### 5.1 签发准入（发码前）

```java
// IssuanceAdmissionService.allowLogin(clientId, userCode)
scopeCodes = scopeService.resolveClientBusinessCodes(clientId);
if (scopeCodes.isEmpty()) return true;              // 逃逸阀: 纯 OIDC 客户端不闸
userCodes  = permissionService.findPermissions(userCode);
return userCodes.stream().anyMatch(scopeCodes::contains);   // fail-closed
```

`AuthorizeIssuanceFilter` 挂 `/oauth2/authorize`：匿名跳过（让登录流程走完），
已登录且拒绝 → 302 `/login.html?error=access_denied`，审计日志 `[签发准入] 拒绝签发...`。

**与自省层同源**：两处读同一套 scope 字典、同一条语义 → 发牌答案就是「这个令牌会不会有业务码」。

### 5.2 端点准入（请求时）

```java
// EndpointAdmissionManager.check()
Rule rule = endpointPolicyService.findRule(method, uri);
if (rule == null)        → 认证档（principal 是 OAuth2AuthenticatedPrincipal 即放行）
if (!rule.enabled())     → 拒绝（status=0 停用行）
switch (requiredAuthority):
  PERMIT_ALL     → 放行
  AUTHENTICATED  → 已认证即放行
  <权限码>       → authenticated && authorities 含该码
```

`Rule` = `record(method, path, requiredAuthority, enabled)`，由内存 `snapshot`（`volatile List`）匹配，
**Ant 路径匹配**兼容 Spring 注册的 `{id}` 占位模式。

### 5.3 端点准入的写入与同步（`EndpointPolicyService.rescan()`）

```text
启动 (EndpointPolicyScanInitializer, ApplicationRunner) → rescan():
  遍历 RequestMappingHandlerMapping 全部 handler
    resolveDomain(controller 包) ∈ {admin, portal, third}?  否则 continue（不入表）
    isInfraPath(/error, /actuator)?                        是则跳过
    库中不存在该 (method, path) → INSERT，required_authority = AUTHENTICATED（宽松默认）
    库中已存在               → 不动（不回写 authority、不剪除）
  reloadSnapshot()
```

**三个"不"**（设计要点）：
- **不回写** authority —— 种子是精确码的唯一权威，避免被扫描默认值冲掉 48 行细码
- **不剪除** —— `domain/source` 两列已删，无所有权信息区分种子行与扫描行，全量剪除可能误删存活细码行（fail-aopen 风险）；失效端点的行是惰性数据（路径不再匹配）
- **页面无 CRUD** —— 管理端只读 GET，写入口只有种子与扫描

## 六、管理端分层

```text
:8001 静态前端 (common.js: App.guard + App.api)
   │  Bearer 透传
   ▼
:8085 iam-admin-bff  (OAuth2 Client admin-app, 授权码 SSO, 独立会话)
   │  Authorization: Bearer <access_token>
   ▼
:9000 /api/admin/**   → Order(3) → EndpointAdmissionManager 按码裁决
```

**字典页只读**：「授权范围」`/api/admin/scopes` 仅 GET；「资源准入」`/api/admin/endpoint-policies` 仅 GET。
