# 详细设计

系统内部实现细节——**各环节怎么工作、关键类在哪**。高层架构见 [概要设计](./概要设计.md)。

## 一、安全链（3 条 FilterChain）

| Order | Bean / 类 | `securityMatcher` | 职责 |
|---|---|---|---|
| 1 | `AuthorizationServerConfig.authorizationServerSecurityFilterChain` | `/oauth2/**`、`/login*`、`/consent`、`/logout`、`/.well-known/openid-configuration`、`/.well-known/oauth-authorization-server` | 协议端点 + 表单登录 + **签发准入过滤器** |
| 2 | `AuthorizationServerConfig.deviceVerificationSecurityFilterChain` | `/activate`、`/device-login` | 设备码激活，独立会话上下文 |
| 3 | `ResourceServerConfig.securityFilterChain` | `/admin/**`、`/biz/**`、`/permitall/**` | `/permitall/**` → `permitAll`；其余 → `anyRequest().access(endpointAdmissionManager)` |

### 1.1 Order(1) 关键装配

```text
authorizationServerSettings
  ├ issuer                    ${iam.issuer}（默认 http://localhost:9000，对外部署必须覆盖）
  ├ authorizationEndpoint     /oauth2/authorize
  ├ tokenEndpoint             /oauth2/token
  ├ deviceAuthorization       /oauth2/device_authorization
  ├ deviceVerification        /oauth2/device/verify
  ├ oidcUserInfo              /userinfo          (未入链，由 UserInfoController 自鉴权)
  ├ clientRegistration        /oauth2/connect/register
  └ oidcLogout                /oidc/logout       (避开 /logout，后者由 LogoutController 处理)
tokenEndpoint providers:
  ├ DeviceCodeGrantAuthenticationProvider (自定义设备码, 含登录准入闸)
  └ SAS 默认 授权码 / 刷新 提供者（无策略包装，准入已移至签发过滤器）
过滤器（按序）:
  SessionExpirationFilter          → SecurityContextHolderFilter 之后
  ActiveClientTrackingFilter       → 解析 Bearer 写入 Session（多客户端会话隔离）
  AuthorizeIssuanceFilter          → 发码前签发准入（混合登录隔离）
```

> `/userinfo` **不入链**的原因：交给自定义 `UserInfoController` 走本地 Redis 内省，
> 避免 `OidcUserInfoFilter` 抢占并引入 `introspection-uri` 的 HTTP 自回环依赖。

### 1.1.1 发行者与签名密钥

| 项 | 配置键 | 说明 |
|---|---|---|
| 发行者标识 | `iam.issuer`（环境变量 `IAM_ISSUER`） | `AuthorizationServerSettings.issuer`、`JwtDecoder` 校验器、内省 `iss` 属性**同源**；对外部署必须改为外部可访问地址 |
| 签名密钥库 | `iam.jwk.keystore-path`（环境变量 `IAM_JWK_KEYSTORE`） | `PersistentJwkStore` 首次启动生成 RSA/EC 密钥并落盘，后续启动复用；多实例需共享同一文件 |

密钥库含私钥，POSIX 系统写入权限收紧为 600；文件损坏时启动直接失败，避免静默轮换导致存量 id_token 全部失效。

### 1.2 Order(3) 资源链

```java
http.securityMatcher("/admin/**", "/biz/**", "/permitall/**")
    .requestMatchers("/permitall/**").permitAll()
    .anyRequest().access(endpointAdmissionManager);
```

## 二、双 SecurityContext 与部分登出

```text
CompositeSecurityContextRepository
  loadContext: 先 DEVICE_SECURITY_CONTEXT → 再 OAUTH2_SECURITY_CONTEXT
  saveContext: OAuth2 链 (Order 1) 接管 formLogin，写 OAUTH2_SECURITY_CONTEXT
  containsContext: 任一存在即 true
```

- 设备激活（Order 2）与浏览器 SSO（Order 1）共用同一 `JSESSIONID`，靠**不同 session 属性 key 隔离**
- `AuthorizationServerConfig.partialLogout(...)`: 按 key 只清对应链路的登录态，全部清空才 `session.invalidate()`
  → 登出设备不会把浏览器 SSO 一起踢掉

## 三、认证流程

### 3.1 授权码（管理后台 / 门户）

```text
浏览器 → BFF(:8085) 302 → 9000 /oauth2/authorize
  ① AuthorizeIssuanceFilter: allowLogin(client_id, user_code)?
       scopeCodes 展开为 0 (纯 OIDC 客户端) → 放行
       否则 userCodes ∩ scopeCodes == ∅ → 302 /login.html?error=access_denied
  ② 未登录 → 302 /login → POST /login (BCrypt 校验, principal = user_code)
  ③ 发授权码 → 302 回 BFF redirect_uri?code=...
  ④ BFF POST /oauth2/token (client_secret_basic) 换 access_token + id_token
```

**登录用户详情**：`PlatformUserDetailsService`（唯一 IdP）
- `loadUserByUsername` / `loadUserByUserCode` → `sys_user` 查凭据，principal name = `user_code`
- 角色由 `PermissionService.findRoleCodes(userCode)` 同库供给（`sys_user_role → sys_role`）
- 角色查询异常 → **降级空角色**（fail-closed，无标签猜测）
- `PlatformDaoProvider` = `DaoAuthenticationProvider` 包它，授权链与设备链共用

### 3.2 设备码

- `DeviceCodeGrantAuthenticationProvider`：轮询态校验，用户确认后按 `user_code` 反查（`loadUserByUserCode`）；
  **含登录准入闸**（查 `client_login_policy`，未命中 `access_denied`）——设备码不经 `/oauth2/authorize`，此处是唯一准入点
- 密码模式 Provider 已删除（OAuth 2.1 废弃该授权类型）

## 四、令牌体系

### 4.0 令牌分工（id_token / access_token / refresh_token）

OAuth2 有 access_token 和 refresh_token，OIDC 在此基础上增加了 **id_token**。三者职责严格分离：

| 令牌 | 用途 | 消费者 | 典型 Claims | 不应包含 |
|---|---|---|---|---|
| **id_token** `JWT` | 证明用户身份（Authentication） | 客户端应用 | `sub`, `preferred_username`, `roles`, `iss`, `aud`(=client_id), `exp` | 资源标识(contacts-api) |
| **access_token** `Opaque` | 调用资源凭证（Authorization） | 资源服务器 | 经内省解析：`sub`, `roles`, `scope`, `client_id`, `exp` | `preferred_username` 等身份声明 |
| **refresh_token** | 续签 access_token | 授权服务器 token 端点 | opaque（不透明） | 不应传给资源服务器 |

**获取与使用流程**：

```text
客户端 → 授权服务器 → 资源服务器

① 授权阶段：客户端请求 scope=openid profile email → 授权服务器返回 code
② 换 token：客户端用 code 换 token → 响应同时包含 access_token、id_token、refresh_token
③ 识别用户：客户端解析 id_token 的 JWT payload 获取 preferred_username、roles 等身份信息，建立本地会话
④ 调 API：客户端用 access_token 作为 Bearer Token 调用 /api/**、/userinfo 等受保护资源
```

> **常见误用**：从 access_token 解码用户身份信息是错误的——正确做法是从 id_token 解码身份，用 access_token 调 API。

**id_token 返回三要素（缺一不可）**：
1. 客户端注册时 scope 包含 `openid`
2. 授权类型不是 `client_credentials`
3. token 请求时 scope 参数显式包含 `openid`

`client_credentials` 模式注册时不含 openid 是正确且必然的——服务间调用没有终端用户，不需要身份令牌。

**openid 使用示例**：

```text
// 授权请求时必须带 openid
GET /oauth2/authorize?response_type=code&client_id=oa-web-app
    &redirect_uri=http://localhost:8081/callback
    &scope=openid profile email        ← openid 必须在此处
    &state=demo

// token 响应中会多出 id_token 字段
{
  "access_token": "eyJraWQ...",
  "id_token":     "eyJraWQ...",   ← 仅当 scope 含 openid 时返回
  "refresh_token": "eyJraWQ...",
  "token_type": "Bearer",
  "expires_in": 7200
}
```

### 4.1 签发

```text
OAuth2TokenGenerator = DelegatingOAuth2TokenGenerator(
    OAuth2AccessTokenGenerator  ← Opaque (REFERENCE) 强制
    JwtGenerator                ← ID Token (RS256, 含 roles / preferred_username)
    OAuth2RefreshTokenGenerator)
```
- Access Token：`accessTokenFormat` 被 `ClientService` 固定写 `REFERENCE`，**不可改为 JWT**（改了会破坏 Redis 内省）
- ID Token claims：`roles`（业务角色）、`preferred_username`（真实用户名，按 `user_code` 反查）、`aud` = client_id

### 4.2 自省（同进程）

```text
RbacAuthoritiesOpaqueTokenIntrospector.introspect(token)
  ├ RedisOpaqueTokenIntrospector（委托）: Redis 查 oauth2_authorization_record → 令牌有效性/属性
  ├ 主判定基于 grant_type 与 client_id，而非「查不到用户」反推
  └ 叠加业务 authorities:
       roleCodes  = sub → sys_user_role → sys_role
       userCodes  = sub → ... → sys_role_permission → sys_permission(启用)
       scopeCodes = client_id → registered_client.scopes → sys_scope(启用) → sys_scope_permission → sys_permission(启用)
       注入 = roleCodes + (userCodes ∩ scopeCodes)     ← fail-closed
  → 返回 EnrichedPrincipal（保留原 attributes，覆写 authorities）
```

**关键类**：
| 类 | 作用 |
|---|---|
| `RbacAuthoritiesOpaqueTokenIntrospector` | 双维交集注入（自省层） |
| `RedisOpaqueTokenIntrospector` | Redis 令牌校验委托，无 HTTP 自回环 |
| `ScopeService` | scope → 权限码展开（`resolveClientBusinessCodes`） |
| `PermissionService` | 角色码 / 权限码查询（同库联表） |

### 4.3 Redis key 设计

| key 模式 | 内容 | TTL |
|---|---|---|
| `oauth2:authorization:*` | 授权记录（令牌校验依据） | 随令牌有效期 |
| `sessionreg:session:{sessionId}` | 会话 hash：principalName / authorities / lastRequest | 会话期 |
| `sessionreg:principal:{userCode}` | 用户 → sessionId 反向索引 | 会话期 |
| `oauth2:client:id:{id}` | 客户端配置缓存（JDBC+Redis 双层） | **1 小时** |
| `oauth2:client:cid:{clientId}` | 同上（按 clientId） | 1 小时 |

> ⚠️ **双层缓存失效规则**：经 `ClientService.save()` 走 API 写会自动 `refreshCache`；
> **绕过 API 的 SQL 直改不会失效**，必须手动 `DEL` 对应 `oauth2:client:*`，否则自省读到旧 `scopes`/`secret`。

### 4.4 撤销

删 `oauth2:authorization:*` 对应 key → 内省 `active=false`。无需 JWT 黑名单。

## 五、准入裁决实现

### 5.1 签发准入（发码前）

```java
// LoginAdmissionService.canLogin(clientId, userCode) — 查 client_login_policy 准入表
rows = clientLoginPolicyMapper.selectList(client_id = clientId AND status = 1);
if (rows.isEmpty()) return false;                   // 无配置 → 拒 (fail-closed)
roleCodes = permissionService.findRoleCodes(userCode);
// ANY 行 → 放行; ROLE 行 → 角色命中; USER 行 → user_code 精确命中; 全未命中 → 拒
```

`AuthorizeIssuanceFilter` 挂 `/oauth2/authorize`：匿名跳过（让登录流程走完），
已登录且拒绝 → 302 `/login.html?error=access_denied`，审计日志 `[签发准入] 拒绝签发...`。

**与自省层解耦**：①登录资格只看准入表，②令牌业务码仍由 用户码 ∩ scope码 决定 ——
改权限码不再影响登录边界（原 `IssuanceAdmissionService` 交集判定已删除）。

### 5.2 端点准入（请求时）

```java
// EndpointAdmissionManager.check()
Rule rule = endpointPolicyService.findRule(method, uri);
if (rule == null)        → 认证档（principal 是 OAuth2AuthenticatedPrincipal 即放行）
if (!rule.enabled())     → 拒绝（status=0 停用行）
if (rule.band() != null) → 档位裁决: PERMIT_ALL 放行 / AUTHENTICATED 已认证即放行 / 未知档拒绝
else                     → PERMISSION 行: authenticated && codes 按 logic 裁决
   logic=ALL → codes.stream().allMatch(令牌含该码)   // 默认, 缺一即拒
   logic=ANY → codes.stream().anyMatch(令牌含该码)
   codes 为空 → 拒绝（防御, 校验/漂移告警层已覆盖）
```

`Rule` = `record(method, path, band, requiredCodes, logic, enabled)`，每次请求由
`findRule()` 实时直查 DB 构造（无内存快照），**Ant 路径匹配**兼容 Spring 注册的 `{id}` 占位模式。

### 5.3 端点准入的运行时模型（`EndpointPolicyService.findRule()`，直查 + 拆表三查）

```text
每个请求 → EndpointAdmissionManager.check():
  findRule(method, uri)  [实时直查, 零内存物化]
    ① 资源行: SELECT ... FROM iam_endpoint
       WHERE service_key = 本服务 AND (method = 请求方法 OR method = 'ANY') ORDER BY id
       → Ant 路径匹配取首个命中
    ② 命中 PERMISSION 行 → 查绑定表 iam_endpoint_permission (endpoint_id)
       → 绑定缺失 = 抛异常 (Fail-Closed)
    ③ 权限表 sys_permission 批量取【当前】权限码集合 (改码零窗口)
       → 绑定权限不可解析 = 抛异常 (Fail-Closed)
    → 档位行 (AUTHENTICATED/PERMIT_ALL): 无绑定, 一查结束; status=0 行直接拒绝
    → 组合裁决: ALL=同时具备 / ANY=任一满足 (permission_logic)
    → 未命中: 返回 null → 表外走认证档 (配置缺省行为, D1 裁定)
  查询/绑定/权限解析异常 → 准入路由器 catch → deny (每请求 Fail-Closed, 绝不放行)

写入 (createPolicy/updatePolicy/deletePolicy, 同一 @Transactional):
  资源行 + 绑定表两表同事务 (permissionIds = 目标全集: null=不改 / []=清空; 档位行强制清空);
  删资源行 FK CASCADE 自动清绑定。保存即时生效 (直查, 无快照刷新环节)。

启动 (EndpointPolicyScanInitializer): 仅做配置漂移告警 —— 推导白名单域接口清单与资源行比对,
  并检查 PERMISSION 行绑定数与权限存在性, 打印缺行/幽灵行/无绑定/权限不可解析清单
  (WARN, 仅提示不拦截; 配置完整性属运维职责)。
```

**设计要点**：
- **改权限码零窗口** —— 令牌侧（内省）与端点侧（准入）都是每请求现算，改码下一请求即一致，无需重启（实测：改名 → 立即 200）；
- **多实例天然同步** —— 各实例现查同一份 DB，不存在新旧快照漂移，无需发布纪律约束混跑；
- **服务无本地业务内存态** —— 与"数据全在 DB、有迹可循"的形态一致；数据量增长后再评估缓存（届时需重新评估改码窗口与失效通知）；
- **写入通道** —— 种子一次性初始化 + 管理页面读写（保存即时生效，B-4 操作审计上线前收口）；启动扫描不写库；
- **1:N 权限组合（拆表）** —— 资源与绑定分离，一端点 1..N 个权限码，`permission_logic` ALL/ANY 组合裁决；
- **保留的 P0-2 地基** —— 绑定表 `permission_id`+FK RESTRICT（页面可安全维护的前提）、`policy_type` 档位显式、`service_key` 命名空间、删除双守卫。

## 六、管理端分层

```text
:8001 静态前端 (common.js: App.guard + App.api)
   │  Bearer 透传
   ▼
:8085 iam-admin-bff  (OAuth2 Client admin-app, 授权码 SSO, 独立会话)
   │  Authorization: Bearer <access_token>
   ▼
:9000 /admin/**   → Order(3) → EndpointAdmissionManager 按码裁决
```

**字典只读**：`/admin/scopes` 仅 GET（明细展示于「客户端管理」编辑弹窗）；「资源准入」`/admin/endpoint-policies` 仅 GET。
