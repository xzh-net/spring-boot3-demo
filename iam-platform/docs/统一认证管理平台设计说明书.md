# 统一认证管理平台设计说明书

> **文档版本**：V5.0（完整版）
> **基线版本**：V4.0
> **更新日期**：2026-08-13
> **变更说明**：V5.0 基于分布式拆分决策定版三大演进：
> 1. **认证中心升级为全量 IdP（IdP 自持用户源）**：`sys_user`（用户名/密码哈希/账号状态）收回 `iam_identity`，认证中心本地校验凭据，登录**零远程凭据调用**（bcrypt 哈希 / 明文密码零跨服务传输）；
> 2. **管理后台接入统一 SSO**：admin-service 作为 OAuth2 Client 接入认证中心 `/login`，废止原“管理后台不参与 SSO”设计；管理端一切操作经用户 token + `hasRole('ADMIN')` 把关；
> 3. **认证中心对外管理 API 三域化**：用户管理 + 客户端管理 + 会话/授权记录管理；资源中心承载业务 RBAC（5 张 sys_* 表）与管理 API。
>
> 在 V4.0 基础上保留 OIDC+PKCE SSO、在线用户与会话管理、设备码等既有方案；新增 <a href="#21-架构演进与关键设计决策（v5）">§21</a> 决策记录。

## 1. 建设目标

建设统一身份认证平台，为门户 Portal、业务系统 A、业务系统 B 提供统一登录能力。

### 目标

- 一次登录，多系统访问
- 任意客户端之间免重复认证（双向 SSO）
- 统一用户身份管理
- 标准 OAuth2 / OIDC 接入
- 各业务系统保持独立会话
- 支持实时权限控制和 Token 撤销
- 支持在线用户与会话可视化管理
- 支持设备码、密码、客户端模式等多种授权模式

## 2. 总体架构

### 2.1 技术选型

- **认证中心**：Spring Authorization Server 1.4.1 + Spring Security 6.4.x
- **OAuth2 协议**：Authorization Code + PKCE / Password / Client Credentials / Device Code
- **OIDC**：ID Token (JWT/RS256) + UserInfo / RP-Initiated Logout
- **Token 格式**：Access Token = Opaque (REFERENCE)，Refresh Token = Opaque，ID Token = JWT
- **存储层**：MySQL 8（客户端配置、用户、授权同意、授权日志） + Redis（token / code / session 运行时状态）

### 2.2 架构图

```
                     用户浏览器
                          |
                  +----------------+
                  | Identity Center|  Spring Authorization Server :9000
                  | OAuth2 + OIDC  |  Opaque Token + JWT(ID Token)
                  +----------------+
                     /      |      \
                 Portal   System A System B
                 Client    Client   Client
                  (BFF)    (Web)    (SPA/移动端)

原则：
- 所有系统均作为 OAuth2 Client 接入认证中心
- 系统之间不直接互相信任
- 应用之间不共享 Token / Cookie
- 认证中心统一维护 SSO 登录状态
```

### 2.3 实际部署模块

| 模块 | 角色 | 类型 | 端口 | 说明 |
|------|------|------|------|------|
| `iam-authorization-server` | Identity Center | Java | 9000 | 认证中心 + 管理后台 + 资源 API |
| `iam-portal-web` | Portal 前端 | Node.js | 8000 | 纯前端，展示客户端列表与 SSO 跳转 |
| `iam-portal-service` | Portal BFF | Java | 8080 | OAuth2 Client (Confidential + PKCE)，持有 client_secret |
| `example/iam-client-web-demo` | System A | Node.js | 8081 | 传统 Web 应用（授权码 / 密码模式） |
| `example/iam-client-device-demo` | System B (设备) | Node.js | 8082 | 设备码模式（RFC 8628） |
| `example/iam-client-mobile-demo` | System C (移动/SPA) | Node.js | 8083 | 授权码 + PKCE（Public Client） |

## 3. 角色定义

### 3.1 Identity Center（认证中心）

职责：

- 用户认证与登录状态管理
- 授权码 / 设备码签发
- Access Token / Refresh Token / ID Token 生成
- Token 校验（Introspection）
- Client 管理与配置
- 在线用户与会话管理
- 管理后台（用户、客户端、授权记录、在线管理、监控）

实现：`iam-authorization-server` 模块（端口 9000）。

### 3.2 Portal（门户）

OAuth 角色：OAuth2 Client + OIDC Client（Confidential Client + PKCE）。

职责：

- 应用导航与用户入口
- 系统跳转
- 通过 SSO 跳转卡片引导用户进入各业务系统

实现：`iam-portal-web`（前端 8000）+ `iam-portal-service`（BFF 8080）。

### 3.3 业务系统

OAuth 角色：OAuth2 Client。

职责：

- 业务处理
- 业务权限控制
- 数据管理

实现示例：

- `example/iam-client-web-demo`：Confidential Client（client_secret_basic + 授权码 / 密码）
- `example/iam-client-mobile-demo`：Public Client（none + 授权码 + PKCE）
- `example/iam-client-device-demo`：Public Client（none + 设备码）

## 4. 协议设计

### 4.1 浏览器认证

采用 **Authorization Code Flow + PKCE**：

```
Client
  │
  │ 1. 跳转认证中心 /oauth2/authorize?code_challenge=xxx
  │
  ▼
认证中心
  │
  │ 2. 用户认证（若已有 SSO Session 则跳过登录页）
  │
  │ 3. 返回 authorization code
  │
  ▼
Client
  │
  │ 4. POST /oauth2/token 换取 Token（带 code_verifier / client_secret）
  │
  ▼
Client
  │
  │ 5. 创建本地 Session
```

### 4.2 支持的授权类型

| Grant Type | 适用场景 | 客户端类型 | 是否签发 ID Token |
|------------|---------|-----------|-------------------|
| `authorization_code` | 浏览器端 | Confidential / Public | ✅（openid scope 时） |
| `refresh_token` | Token 续期 | Confidential ✅ / Public ❌（RFC 8252） | ✅（openid scope 时） |
| `password` | 信任客户端直登 | Confidential | ✅（openid scope 时） |
| `client_credentials` | 服务间调用 (M2M) | Confidential | ❌ |
| `urn:ietf:params:oauth:grant-type:device_code` | 无浏览器设备 | Public | ✅（自定义 Provider 支持） |

### 4.3 ID Token 签发条件

同时满足以下三个条件才会签发 ID Token：

1. 客户端注册时包含 `openid` scope
2. 授权类型不是 `client_credentials`
3. Token 请求中包含 `openid` scope

## 5. Token 设计

### 5.1 Token 类型

| Token | 格式 | 用途 | 存储位置 |
|-------|------|------|---------|
| ID Token | JWT (RS256) | OIDC 身份声明 | 不落库，客户端持有 |
| Access Token | Opaque (REFERENCE) | API 访问授权 | Redis |
| Refresh Token | Opaque (REFERENCE) | 获取新的 Access Token | Redis |
| Authorization Code | Opaque | 授权码换取 Token | Redis (短 TTL) |
| Device Code | Opaque | 设备码轮询授权 | Redis |
| User Code | Opaque | 用户输入确认 | Redis |

### 5.2 Token 原则

- Access Token **不包含业务信息**，为随机字符串
- 业务系统**不能**解析 Access Token，**不能**自行验证签名
- 业务系统**必须**调用 `/oauth2/introspect` 完成 Token 校验
- Access Token 短生命周期（默认 2h，可按客户端配置）
- Refresh Token 轮换（`reuseRefreshTokens=false`）
- 支持主动撤销（删 Redis key，无需 JWT 黑名单）

### 5.3 Token 生成器链路

```
OAuth2TokenGenerator
   ├── OAuth2AccessTokenGenerator  ← 优先 Opaque 格式
   ├── JwtGenerator                ← ID Token 使用
   └── OAuth2RefreshTokenGenerator
```

> **关键约束**：`OAuth2AccessTokenGenerator` 必须在 `JwtGenerator` 之前，确保 Access Token 全局为 Opaque (REFERENCE)，即使 DB 中配置为 SELF_CONTAINED 也会被强制覆盖。

## 6. Token 流程

### 6.1 登录成功签发

认证中心在登录成功后生成：

```
authorization_code  → Redis (TTL ≈ 5min)
access_token        → Redis (TTL ≈ 2h)
refresh_token       → Redis (TTL ≈ 12h)
id_token (JWT)      → 不落库，直接返回客户端
```

### 6.2 Redis 存储结构

```
oauth2:auth:{id}              → OAuth2Authorization 完整对象 (JSON)
oauth2:auth:access:{token}    → authorizationId
oauth2:auth:refresh:{token}   → authorizationId
oauth2:auth:code:{code}       → authorizationId
oauth2:auth:device:{code}     → authorizationId
oauth2:user:{principalName}   → Set<authorizationId>
oauth2:sso_session:{ssoId}    → Set<authorizationId>
```

所有 key 带 TTL，与对应 Token 过期时间对齐。撤销时直接删除 key，资源服务器 introspect 查不到即返回 401。

### 6.3 客户端索引跳过规则

当 `principalName` 为已注册的 `client_id` 时（即 `client_credentials` 模式），跳过写入 `oauth2:user:{}` 索引，避免 M2M 调用污染用户会话视图。

## 7. Token 校验设计

业务系统收到请求：

```
Client API
   │
   │ Authorization: Bearer <opaque_token>
   ▼
业务系统
   │
   │ POST /oauth2/introspect
   │   Authorization: Basic <client_credentials>
   │   Body: token=<opaque_token>
   ▼
认证中心返回：
{
  "active": true,
  "client_id": "system-a",
  "username": "zhangsan",
  "scope": "openid profile read",
  "exp": 1234567890,
  "aud": ["contacts-api"]
}
```

业务系统根据返回结果建立访问上下文。

> **RFC 7662 约束**：Token 无效时返回 `200 + {active: false}`，**而非 401**。客户端按钮状态判断需同时检查 `status === 401` 或 `(status === 200 && active === false)`。

## 8. Session 设计

### 8.1 隔离原则

认证中心 Session 和业务 Session **完全分离**，各系统生命周期独立。

```
Identity Center  → LOGIN_SESSION (SSO Session)
Portal (BFF)     → PORTAL_SERVER_SESSION
System A         → CLIENT_8081_SESSION
System B (设备)  → CLIENT_8082_SESSION
System C (移动)  → CLIENT_8083_SESSION
Admin            → ADMIN_SERVER_SESSION（V5 起作为 OAuth2 Client 会话参与统一 SSO，不独立于认证中心）
```

### 8.2 Session 域隔离矩阵

| 退出操作 | ADMIN | PORTAL | CLIENT_8081 | CLIENT_8082 | CLIENT_8083 |
|---------|-------|--------|-------------|-------------|-------------|
| 退出 ADMIN | 销毁 | 保留 | 保留 | 保留 | 保留 |
| 退出 PORTAL | 保留 | 销毁 | 保留 | 保留 | 保留 |
| 退出 8081 | 保留 | 保留 | 销毁 | 保留 | 保留 |
| 退出 8082 | 保留 | 保留 | 保留 | 销毁 | 保留 |
| 退出 8083 | 保留 | 保留 | 保留 | 保留 | 销毁 |

### 8.3 SecurityContext 隔离

通过不同 HttpSession attribute key 隔离 SecurityContext：

| Context Key | 用途 | 所属 FilterChain |
|-------------|------|------------------|
| `PORTAL_SECURITY_CONTEXT` | OAuth2 授权码登录态 | Order(1) OAuth2 |
| `DEVICE_SECURITY_CONTEXT` | 设备验证流程 | Order(5) Device |

> **V5 变更**：管理后台的 SecurityContext（原 `ADMIN_SECURITY_CONTEXT` / Order(3) Admin 链）随“管理域独立 + 统一 SSO”移除——认证中心不再存在独立的管理员表单链，Admin 会话由 iam-admin-service 自身管理（`ADMIN_SERVER_SESSION`），不再与 OAuth2/设备链共用 HttpSession。

OAuth2 链使用 `CompositeSecurityContextRepository`，读取时 `DEVICE → PORTAL` 回退，`saveContext` 为 no-op。

### 8.4 客户端会话 Cookie 隔离

各服务通过 `server.servlet.session.cookie.name` 设置独立 Cookie 名，避免 localhost 下 JSESSIONID 互相覆盖：

| 服务 | Cookie 名 |
|------|-----------|
| 认证中心 | `JSESSIONID`（默认） |
| iam-portal-service | `PORTAL_SERVER_SESSION` |
| web-app | `WEB_APP_SESSION` |
| mobile-app | `MOBILE_APP_SESSION` |
| device-app | `DEVICE_APP_SESSION` |

## 9. SSO 设计

### 9.1 SSO 基础

所有应用均作为 OAuth2 Client 接入认证中心。认证中心维护统一的 SSO Session，浏览器携带 `JSESSIONID` 跨应用跳转时，认证中心识别已有登录态即可直接签发 code。

### 9.2 Portal → System A（正向 SSO）

```
Portal登录
   │
   │ 建立 SSO Session
   ▼
访问System A
   │
   │ System A 跳转 /oauth2/authorize
   ▼
认证中心发现已有 SSO Session
   │
   │ 直接签发 code（无需重新输入密码）
   ▼
System A 换 Token，创建独立 CLIENT_SESSION
```

### 9.3 System A → Portal（反向 SSO）

A 不直接认为 Portal 已登录，应重新发起 OIDC 请求：

```
A 返回 Portal
   │
   │ 发起 /oauth2/authorize?client_id=portal-app&prompt=none
   ▼
认证中心检查 SSO Session
   │
   ├─ 有 Session → 返回 code（静默授权）
   └─ 无 Session → 返回 error=login_required（客户端转正常登录流程）
   ▼
Portal 换 Token，创建 PORTAL_SESSION
```

### 9.4 PKCE 流程

适用于 Public Client（mobile-app）以及强制启用 PKCE 的 Confidential Client（portal-app）。

```
1. 客户端生成 code_verifier (32 字节随机数, Base64URL = 43 字符)
2. 计算 code_challenge = BASE64URL(SHA256(ASCII(code_verifier)))
3. 授权请求带 code_challenge + code_challenge_method=S256
4. Token 请求带 code_verifier 明文
5. 认证中心校验 SHA256(code_verifier) == code_challenge，一致则签发 Token
```

### 9.5 Portal 侧 PKCE 实现

iam-portal-service 虽为 Confidential Client，但客户端注册时已设置 `requireProofKey=true`（现代安全实践，RFC 7636 + OAuth 2.1）。通过自定义实现：

- `pkceAuthorizationRequestResolver`：生成 code_verifier，计算 code_challenge，存入 OAuth2AuthorizationRequest 的 additionalParameters
- `pkceTokenResponseClient`：从授权请求的 additionalParameters 取出 code_verifier，拼到 token 请求表单

### 9.6 SSO 跳转策略（统一跳客户端首页）

`PublicClientController` 不直接为每个客户端生成授权 URL，而是统一返回客户端首页 URL。客户端首页自行检测本地 session：

- 已有 session → 直接显示已登录页（不发新 Token，避免在线管理出现重复会话）
- 无 session → 客户端自行发起 `/oauth2/authorize` 授权流程

PKCE 客户端本来就无法由门户代生成 code_challenge，只能跳首页。

### 9.7 mobile-app 的 SSO 返回机制

Public Client 不签发 refresh_token（RFC 8252 安全策略），通过 `/return-to-portal` 端点实现 SSO 返回：

1. 跳转到认证中心 `/oauth2/authorize?client_id=portal-app&prompt=none`
2. 回调到 `/portal-sso-callback`
3. 若有 SSO Session → 拿到 code → 正常换 Token → 创建 PORTAL_SESSION
4. 若无 SSO Session → 返回 `login_required` → 转正常登录流程
5. 回调类型 `self-silent` 允许客户端用 code_verifier 完成 Token 交换

## 10. Logout 设计

### 10.1 三种退出模式

| 模式 | 触发方 | 效果 |
|------|--------|------|
| 单系统退出 | 客户端自身 | 仅销毁自身 Session，保留其他系统登录 |
| 全局退出 | 任意客户端 | 销毁 SSO Session + 所有客户端 Token |
| 管理员强制下线 | 管理后台 | 按用户 / 按 SSO 会话强制下线 |

### 10.2 客户端完整退出（两步操作）

OAuth2 客户端完整退出必须执行：

1. **POST /oauth2/revoke**（RFC 7009）吊销 access_token 和 refresh_token
2. **GET /logout?redirect=...**（或带 `post_logout_redirect_uri`）销毁 PORTAL HttpSession

单独执行任一步都无法实现真正退出。

### 10.3 LogoutController 端点

`LogoutController` 同时支持：

- OIDC 标准参数 `post_logout_redirect_uri`
- 自定义参数 `redirect`

以兼容不同客户端的退出重定向需求。

### 10.4 OIDC End Session 端点配置

通过 `.oidcLogoutEndpoint("/logout")` 显式配置 OIDC end_session_endpoint，与实际 logout handler 匹配。

> **陷阱规避**：Spring Security 6.4 的 `OidcClientInitiatedLogoutSuccessHandler.determineTargetUrl()` 通过 `providerDetails.getConfigurationMetadata().get("end_session_endpoint")` 获取端点，application.yml 中的 `logout-uri` 不会被映射到该 metadata key。当 `end_session_endpoint` 为 null 时，handler 回退到 `SimpleUrlLogoutSuccessHandler` 默认行为（跳到 `/`），触发 OAuth2 重新登录循环。修复方案：实现自定义 `LogoutSuccessHandler`，手动调用 `/oauth2/revoke` 后 302 跳到 `/logout`。

### 10.5 partialLogout 实现

退出时使用 `partialLogout()` 而非直接 `session.invalidate()`，避免销毁整个 HttpSession 导致跨 SecurityContext 退出：

- `/admin/logout` → `partialLogout(ADMIN_CONTEXT_KEY)` 仅清除管理员认证
- `/logout` → `partialLogout(DEVICE_CONTEXT_KEY)` 清除设备认证，保留管理员
- `anyLeft=true` 时仍需调用 `sessionRegistry.removeSessionInformation()`，否则退出用户仍显示在在线列表

## 11. 权限模型

```
User → Role → Permission → Resource → Client
```

- 认证中心负责**身份**（认证）
- 业务系统负责**业务权限**（授权）
- ID Token 携带真实 authorities（通过 `PortalUserDetailsService` 加载）

## 12. 数据设计

### 12.1 MySQL 表结构

| 表 | 用途 | 关键字段 |
|----|------|---------|
| `sys_user` | 系统用户 | id, username, password(BCrypt), role, enabled |
| `oauth2_registered_client` | 客户端配置 | client_id, client_secret, grant_types, redirect_uris, scopes, client_settings, token_settings |
| `oauth2_authorization_consent` | 授权同意 | registered_client_id, principal_name, authorities, first_grant_time |
| `oauth2_authorization_record` | 授权历史日志 | principal_name, client_name, granted_authorities, grant_type, status, grant_time, revoke_time |

> **不建 `oauth2_authorization` 表**，运行时状态（access_token / refresh_token / code / device_code）全部在 Redis，撤销即删 key。

#### 12.1.1 数据库归属（V5 拆分定版）

| 库 | 归属服务 | 表 | 说明 |
|----|----------|----|------|
| `iam_identity` | 认证中心（全量 IdP） | `oauth2_authorization_consent`、`oauth2_authorization_record`、`oauth2_registered_client`、**`sys_user`** | 客户端配置 + 授权同意/记录 + **用户凭据主库（用户名/密码哈希/账号状态）**，认证中心本地校验，登录零远程凭据调用 |
| `iam_authorization` | 资源中心 | `sys_user`（业务视图）、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission` | 业务 RBAC：角色/权限/授权关系；用户账号由认证中心权威写入后同步业务视图 |
| `iam_portal` / `iam_admin` | 门户 / 管理域 | 暂无（二期） | 门户配置、管理审计/审批等 |

> **一致性约束**：`sys_user` 双库存在——认证中心为权威写入方（凭据/状态），资源中心持有业务视图（供 RBAC 联查）。禁用/改密/删除由认证中心触发并向资源中心同步（见 §21 决策 D9）。
> **临时接线**：门户应用列表暂以 `oauth2_registered_client` 承接，应用目录表 `iam_application` 二期引入（见 §21 决策 D8）。

### 12.2 客户端配置示例

| client_id | 模式 | 认证方式 | redirect_uri | 关键设置 |
|-----------|------|---------|--------------|---------|
| `portal-app` | 授权码 + PKCE | client_secret_basic | `http://localhost:8080/login/oauth2/code/portal-app-oidc` | requireProofKey=true |
| `web-app` | 授权码 / 密码 | client_secret_basic | `http://localhost:8081/callback` | requireAuthorizationConsent=true |
| `device-app` | 设备码 | none | — | — |
| `mobile-app` | 授权码 + PKCE | none | `http://localhost:8083/callback` | requireProofKey=true |
| `service-app` | 客户端模式 | client_secret_basic | — | accessTokenTimeToLive=PT30M |

### 12.3 客户端配置读写约束

- `JdbcRegisteredClientRepository.parseTokenSettings()` 默认 `accessTokenFormat=REFERENCE`
- `ClientService.create() / update()` 显式设置 `accessTokenFormat=REFERENCE`
- DB 配置被强制覆盖为 REFERENCE，无法通过管理后台修改
- `ClientSettings` 字段读取使用 camelCase（`requireProofKey`, `requireAuthorizationConsent`）
- `TokenSettings` 字段读取使用 dotted kebab-case（`reuse-refresh-tokens`）
- 客户端配置变更后自动刷新 Redis 缓存，无需重启服务

## 13. Redis 设计

### 13.1 OAuth2 运行时数据

```
oauth2:auth:{authorizationId}        → OAuth2Authorization JSON
oauth2:auth:access:{token}           → authorizationId
oauth2:auth:refresh:{token}          → authorizationId
oauth2:auth:code:{code}              → authorizationId
oauth2:auth:device:{deviceCode}      → authorizationId
oauth2:user:{principalName}          → Set<authorizationId>
oauth2:sso_session:{ssoSessionId}    → Set<authorizationId>
oauth2:client:{clientId}             → RegisteredClient JSON (缓存)
```

所有 key 带 TTL，与对应 Token 过期时间对齐。

### 13.2 Session 数据

Spring Session + Redis 持久化：

- 管理员 HttpSession 数据持久化到 Redis，防止服务重启丢失登录状态
- `RedisSessionRegistry` 跟踪 SSO 会话，包含：
  - `creationTime`：会话创建时间（仅登录时写入，作为"登录时间"）
  - `lastAccessTime`：最后请求时间（作为"最近访问时间"）
  - `expired`：过期标记（`markSessionExpired()` 持久化到 Redis Hash）

### 13.3 在线管理索引

```
session:principal:{username}    → Set<sessionId>
session:client:{clientId}       → Set<sessionId>  (活跃客户端跟踪)
```

由 `ActiveClientTrackingFilter` 解析 Bearer Token 后写入。

## 16. 在线用户与会话管理

### 16.1 层级模型

```
User (用户)
  └─ SSO Session (一次认证产生的统一登录会话)
       └─ Client Session (该 SSO Session 使用过的客户端)
            ├─ Portal
            ├─ Web-App
            └─ Mobile-App
```

### 16.2 关键关联

`OAuth2Authorization` 通过 `__sso_session_id` attribute 与 SSO Session 关联：

- `enrichWithClientInfo()` 注入 ssoSessionId（已有则保留，避免 token 刷新时覆盖）
- `save()` 写入 `oauth2:sso_session:{ssoSessionId}` → Set<authId> 索引
- `remove()` 清理该索引
- `findBySsoSessionId(ssoSessionId)` 返回该 SSO 会话下所有 OAuth2Authorization
- `revokeBySsoSessionId(ssoSessionId)` 撤销该 SSO 会话下所有授权

### 16.3 退出按 SSO 会话精确撤销

`LogoutController.logout()` 优先调用 `revokeBySsoSessionId(ssoSessionId)`，仅撤销当前设备 SSO 会话关联的客户端会话；若 ssoSessionId 为 null 或返回 0，fallback 到原 principalName 全量撤销逻辑。

### 16.4 管理 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/online/users` | 统一在线用户列表（合并 SSO + 客户端会话） |
| GET | `/admin/users/{id}/sessions` | 用户会话层级视图 |
| POST | `/admin/users/{id}/logout` | 按用户踢下线（所有设备退出） |
| POST | `/admin/sessions/{id}/logout` | 按 SSO 会话踢下线（仅指定设备退出） |

保留原有 `/admin/user/api/...` 端点向后兼容。

### 16.5 在线管理 UI 设计

采用**上下结构**布局，一屏展示：

- 上方：**管理员列表**（蓝色徽章），列：用户名、会话数、上次登录、操作
- 下方：**客户端列表**（绿色徽章），列：用户名、客户端、授权类型（卡片样式）、登录时间、TOKEN过期、操作

交互要求：

- 刷新按钮同时刷新管理员列表和客户端列表（并行加载）
- 独立的空状态提示
- SSO 会话卡片按钮文案为「终止会话」
- 客户端会话行按钮文案为「撤销令牌」
- 客户端会话详情：
  - 登录时间列后添加🔑图标按钮，悬浮显示 Access Token，点击复制
  - TOKEN 过期列后添加🔄图标按钮，悬浮显示 Refresh Token，点击复制
  - 登录时间 = `accessToken.issuedAt`
  - TOKEN 过期 = `accessToken.expiresAt`
- SSO 会话：
  - 登录时间 = `creationTime`（仅登录时写入）
  - 最近访问时间 = `lastAccessTime`（最后请求时间）
- 强制下线操作需有成功/失败提示（alert）
- 管理后台下线客户端用户后，客户端在 access_token 过期前仍可访问资源（OAuth2 标准行为，需在提示中说明）

### 16.6 用户管理联动

`UserService` 的以下操作均触发 `kickOfflineSafely → revokeUserAll`：

- `enable(false)` 禁用用户
- `delete()` 删除用户
- `update()` 修改用户信息
- `resetPassword()` 重置密码

## 17. 管理后台设计

### 17.1 路径与页面

| 路径 | 页面 | 能力 |
|------|------|------|
| `/admin/login.html` | 管理员登录 | 独立登录页（ROLE_ADMIN） |
| `/admin` | 开发手册首页 | 内置对接说明 |
| `/admin/user` | 用户管理 | CRUD、启用/禁用、重置密码 |
| `/admin/client` | 客户端管理 | CRUD、重置密钥 |
| `/admin/authorization` | 授权记录 | 查询授权同意（主表）+ 授权历史（子表）、撤销 |
| `/admin/online` | 在线管理 | 管理员列表 + 客户端列表，强制下线 |
| `/admin/monitor` | 运行监控 | 服务状态监控 |

### 17.2 认证隔离（V5 改为统一 SSO）

**V5 定版**：管理后台接入统一 SSO，废止原“管理后台不参与任何 SSO 流程”设计。

- 管理员即“拥有 `ROLE_ADMIN` 角色的用户”，走认证中心 `/login`（OAuth2 授权码）
- admin-service = OAuth2 Client（Confidential），登录回调用 `ID Token`/claims 校验 `roles` 含 `ADMIN`，否则拒绝
- 认证中心管理 API（用户/客户端/会话）与资源中心管理 API（角色/权限）统一由 admin-service 转发用户 token 调用，各接口服务端 `hasRole('ADMIN')` 二次把关
- 退出语义：admin-service 登出仅清自身 `ADMIN_SERVER_SESSION` + 吊销自身 token，**不触发**认证中心全局 SSO 登出 → 保持“退出不影响门户/业务系统会话”
- 原 `AdminUserDetailsService` / Order(3) 管理员表单链随管理域迁出认证中心而移除

> 遗留说明：V4.0 及更早版本的“管理后台不参与 SSO、独立 ADMIN 会话”为单体同进程隔离设计；V5 拆分后管理域为独立服务 + 独立 Cookie，该隔离目标已由服务边界达成，故可安全回归统一 SSO。

### 17.3 模板渲染

管理后台页面由 Controller 渲染 Thymeleaf 模板（`templates/admin/`），**不可直接通过 URL 访问静态资源**。

## 18. 门户拆分设计

### 18.1 拆分动机

将原单体中的门户模块拆分为前后端分离架构，提升可维护性：

- `iam-portal-web`（端口 8000）：纯前端，零依赖 Node.js，仅负责展示客户端列表与 SSO 跳转
- `iam-portal-service`（端口 8080）：BFF，持有 client_secret，处理 OAuth2 授权码流程

### 18.2 iam-portal-service 职责

- 持有 `portal-app` 客户端的 `client_secret`
- 处理 OAuth2 授权码登录流程（含 PKCE）
- 提供 REST API 给前端：`GET /api/user/me`、`GET /api/clients`
- 管理 HttpSession 存储 OAuth2 token
- 登出时通过 OIDC RP-Initiated Logout 通知认证中心
- CORS 配置允许 iam-portal-web 前端跨域调用（携带 Cookie）

### 18.3 iam-portal-web 职责

- 代理 `/api/*` 请求到 iam-portal-service（透传 `PORTAL_SERVER_SESSION` Cookie）
- 渲染门户首页、登录入口、退出按钮
- 通过 iam-portal-service 获取可用客户端列表

### 18.4 客户端列表来源

认证中心的 `PublicClientController`：

- 跳过 `portal-app` 自身
- 跳过设备码客户端（`device-app`）
- 仅返回支持授权码模式的客户端
- 统一返回客户端首页 URL（让客户端自行检测 session）

## 20. 最终架构总结

```
                     Identity Center (:9000)
              Spring Authorization Server 1.4.1
              OAuth2 + OIDC Provider + 管理后台
                         |
          --------------------------------
          |              |              |
        Portal (:8000 + :8080)    Web-App (:8081)    Mobile-App (:8083)
        Confidential + PKCE        Confidential       Public + PKCE
                         |
                   Device-App (:8082)
                   Public + Device Code

Token:
  OIDC ID Token       → JWT (RS256)
  OAuth Access Token  → Opaque (REFERENCE)
  Refresh Token       → Opaque (REFERENCE)
  Public Client       → 不签发 refresh_token

Session:
  各系统独立维护
  ADMIN / PORTAL / CLIENT_xxx 按域隔离
  CompositeSecurityContextRepository 回退读取

权限:
  认证中心统一身份
  业务系统控制授权
  ID Token 携带 authorities

管理后台:
  用户/客户端/授权记录/在线管理/运行监控
  按用户踢 / 按 SSO 会话踢
  用户操作联动会话撤销
```

### 该方案满足

- ✅ 企业级 SSO（双向）
- ✅ 多系统接入（4 种 OAuth2 模式）
- ✅ Token 实时撤销（删 Redis key）
- ✅ 动态权限控制（ID Token 携带 authorities）
- ✅ 在线用户与会话可视化管理
- ✅ 管理员强制下线（按用户 / 按 SSO 会话）
- ✅ 用户操作联动会话撤销（禁用 / 重置密码）
- ✅ 门户前后端分离架构
- ✅ 移动端扩展和 IoT 设备接入
- ✅ 多环境配置（dev / local / prod）

## 21. 架构演进与关键设计决策（V5）

> 章节目标：记录 V5 拆分过程中形成的**关键设计决策与取舍**（ADR 风格），使“为什么这么做”可追溯。未在本章列出的旧方案、被否决方案均在此归档。

### 21.1 决策 D1：认证中心升级为全量 IdP（IdP 自持用户源）

- **背景**：业务账号 `sys_user`（含 bcrypt 密码哈希）此前规划归资源中心（iam_authorization），导致认证中心无法本地校验密码，需远程调用资源中心取哈希。
- **决策**：将 `sys_user`（用户名/密码哈希/账号状态）**收回 `iam_identity`**，认证中心本地校验（`bcrypt.matches`），登录**零远程凭据调用**——bcrypt 哈希与明文密码均不跨服务传输。
- **被否决方案归档**：
  - *哈希外传*（认证中心远程取哈希回来比对）：每次登录哈希离开库，接口若失控 = 批量拖哈希 + 离线爆破，否决；
  - *credential broker*（认证中心把明文密码交给资源中心校验）：资源中心校验接口成为在线口令预言机，需内网鉴权/限流双兜底，作为复杂度更高、安全性次于 IdP 自持的方案否决。
- **收益**：哈希/明文零外传、登录链路不依赖资源中心存活、防爆破可落位本地锁定策略。

### 21.2 决策 D2：管理 API 跟随数据所有权（三域模型）

- **原则**：认证中心只对外提供“它拥有数据”的管理 API，不暴露非自有数据的管理接口。
- **认证中心管理 API（三域）**：`/api/admin/users`（账号/凭据/启用锁定）、`/api/admin/clients`（客户端/密钥重置）、`/api/admin/sessions|records`（在线会话/踢下线/授权记录）。
- **资源中心管理 API**：`/api/admin/roles`、`/api/admin/permissions`（业务 RBAC）。
- 统一访问模型：admin-service 转发**用户 token**（Bearer + introspection + `hasRole('ADMIN')`），身份即用户，非独立 cl2 凭证。

### 21.3 决策 D3：管理后台接入统一 SSO

- 管理员 = 拥有 `ROLE_ADMIN` 角色的用户；admin-service 为 OAuth2 Client，登录走认证中心 `/login`。
- 撤销“管理后台不参与 SSO”旧设计（单体同进程隔离目标已由服务边界达成）。
- 退出语义保留：admin-service 登出仅清自身会话 + 吊销自身 token，不触发全局 SSO 登出（见 §8.2 退出矩阵）。

### 21.4 决策 D6：内部接口安全规范（适用所有跨服务调用）

凡认证中心 ↔ 资源中心内部接口，强制满足：
1. **内部鉴权**：客户端凭证模式（client_credentials）+ introspection，或内部共享 Token Header；**禁止 permitAll**；`controller/internal` 以硬规则收敛（仅认证中心 M2M `resource-server` 可调，V6.10）；
2. **内网隔离**：仅指定服务网段可达，禁止暴露公网；
3. **最小数据**：只传/回职责最小字段；角色供给接口**不得含凭据**；
4. **传输加密**：生产 HTTPS/mTLS（dev localhost 明文仅限开发）；
5. **限流与审计**：防枚举/重放，调用留日志。

### 21.5 决策 D8：门户应用列表临时承接

- 应用目录（`iam_application`）与 OAuth2 客户端（`oauth2_registered_client`）是不同的概念；架构层面应用目录应归资源中心。
- **现状（2026-08）已落地**：`iam_application / iam_application_channel / iam_app_authorization` 三表 + 管理端三级 API + 门户 `mine` 按 `visible + 授权` 过滤，`iam_org` 组织表就绪；渠道挂 `sso_client_id`，**密钥零落库方案 A**——明文密钥仅创建/重置一次性返回，资源中心不落库（落地细节见 `docs/数据模型设计.md` §4.2；渠道密钥签发联动尾项见 `docs/改造清单-二级应用.md` B2）。

### 21.6 决策 D9：sys_user 双库一致性

- `sys_user` 权威写入方 = 认证中心（凭据/状态/禁用/改密）；资源中心不镜像用户表（V6.2 已删影子用户），业务 RBAC 与授权按业务用户编码 `user_code` 寻址。
- 联动机制：认证中心对用户做删除/重置/禁用等写操作后，触发资源中心按 user_code 清理授权（`DELETE /api/admin/users/{userCode}/data`，管理 M2M 服务凭证 `admin-m2m`，V6.9 迁入管理端能力）并强制下线会话；内省判定改按 grant_type + client_id 白名单，不再由“本地查不到用户”反推服务令牌。
- **状态（2026-08）：已解决，不再双写**（原 D9 决策项归档为已完成，见 `docs/改造清单-一级框架.md` §2）。

### 21.7 已知取舍与残留风险（与业界标准对照）

| 编号 | 项 | 状态 | 计划 |
|------|----|------|------|

| R2 | 认证中心敏感数据集中（账号+凭据+客户端+会话） | 已约束 | 管理 API 要求 ADMIN + 审计 + 未来 MFA |

## 22. 服务对外能力说明

本章以总结形式分类描述平台内各服务的对外能力，是安全面划分与跨服务联调的权威依据；
尚未规划或未实现的服务先留空目录，后续逐步补齐。

### 22.1 iam-authorization-server（认证中心，:9000）

平台唯一身份认证与授权中心。对外提供**两类接口能力**：

**（一）协议层能力 —— 面向所有 OAuth2 客户端 / 浏览器**

| 分类 | 能力 |
|------|------|
| 认证授权 | 授权码、设备码、密码、刷新令牌、客户端模式等全量 grant_type 的签发 |
| Token 生命周期 | Token 签发 / 内省 / 撤销 / 签名公钥（JWKS） |
| OIDC 会话 | UserInfo、统一登录页、登出、授权同意、OIDC 发现与动态注册、设备激活 |

- 特征：access_token 为 Opaque（Redis 撤销即失效），id_token 为 JWT（RS256）。
- 适用：门户、管理后台、各演示客户端等一切需要认证的应用。

**（二）管理端能力 —— 单独面向管理后台（iam-admin-service）开发**

| 分类 | 能力 |
|------|------|
| 用户 | 用户增删改查、启用 / 禁用、重置密码、用户会话清理 |
| 客户端 | 客户端增删改查、重置密钥 |
| 会话 | 统一在线用户、用户会话层级、按用户 / 按 SSO 会话踢下线、按用户撤销令牌 |
| 授权记录 | 授权同意主表、授权历史、取消授权 |

- 认证方式：Bearer + `ROLE_ADMIN`，仅管理后台经 OAuth2 登录后携带令牌调用。

**明确不对外提供**：健康检查（`/health` 已随管理台剥离后删除）、客户端目录（门户应用列表规划归资源中心）、任何业务 / 公开接口（遵循「认证中心不提供业务能力」原则）。

> **接口明细（端点 / 参数 / 调用示例）**：[对外接口说明 §1 认证中心](./对外接口说明.md#auth-center)

### 22.2 iam-resource-service（资源中心，:9010）

业务 RBAC 资源中心，持有 `iam_authorization` 库（角色 / 权限 / 关联）。
对外提供**三类接口能力**（管理端 / portal 端 / 开放能力）按调用方身份分域，另有**不需要权限的接口示例**（`controller/permitall`，归 other 域 + PERMIT_ALL，仅测试接口）与**服务间内部能力**供认证中心 M2M（不属对外分类）：

**（一）管理端能力 —— 面向管理后台（iam-admin-service）**

| 分类 | 能力 |
|------|------|
| 角色 | 角色列表、新增、修改（可重绑权限）、删除 |
| 权限 | 权限列表、新增、修改、删除 |
| 用户生命周期 | 删除 users 时联动清理（角色绑定 + USER 主体应用授权，`DELETE /api/admin/users/{userCode}/data`，幂等） |

- 调用路径：`/api/admin/roles`、`/api/admin/permissions`、`/api/admin/users/{userCode}/data`（Bearer + `ADMIN_SERVICE_TOKEN`），管理后台经 admin-service 登录后 Bearer 透传调用。
- 用户生命周期联动清理以**管理 M2M 服务凭证**（`admin-m2m` 客户端 client_credentials，资源中心内省注入 `ADMIN_SERVICE_TOKEN`）由认证中心触发（V6.9，原 `/api/internal/user/{userCode}/data` 迁入），遵守「管理写归 `/api/admin/**`，`controller/internal` 仅只读内省」规范。
- 与管理端平级：portal 端、业务系统均无此域权限。

> 现状：用户 ↔ 角色分配（`assignRolesToUser` / `listRoleIdsOfUser`）已实现于服务层，但**尚未暴露 REST 接口**。管理台"按人查/分配角色"应作为**管理端能力**新增 `/api/admin/users/{id}/roles`（`ADMIN_SERVICE_TOKEN` + admin-app 白名单），而非复用内部接口。

**（二）portal 端能力 —— 面向门户（iam-portal-service / portal-web）**

portal 是特权客户端（与管理端平级），门户经其 BFF 拉取当前人员可见客户端做 SSO 跳转卡片：

| 分类 | 能力 |
|------|------|
| 门户应用中心卡片 | 当前人员可见客户端列表（按应用授权过滤） |

- 调用路径：`/api/public/clients/mine`（portal 端能力，V6.6 起要求 `PORTAL_SERVICE_TOKEN`（门户服务凭证，仅门户应用客户端 `portal-app` 签发令牌由内省器注入）+ 门户客户端白名单 `authserver.portal-client-ids` 双闸门）。
- 由门户 BFF（iam-portal-service）携带用户 Bearer 调用；服务端内省取 `user_code` + RBAC 角色，按 `iam_application.visible` + `iam_app_authorization` 过滤返回可见应用渠道。

**（三）开放能力 —— 面向三方业务客户端（任意凭证 + 客户端订阅，`controller/capability`，V6.5）**

| 分类 | 能力 |
|------|------|
| 通讯录示例 | 返回 sub 对应的 DB 身份、角色、权限 + 通讯录数据（当前硬编码）；对应能力编码 `contact:query` / `contact:detail` |

- 调用路径：`/api/capability/contacts`、`/api/capability/contacts/{id}`（V6.5 起由 `/api/contacts` 迁入开放能力命名空间）。
- 能力准入（登记制）：任意凭证用户令牌 + 令牌 client_id 已订阅对应能力（`iam_capability_subscription` status=1 且在有效期内）并按 `required_scopes` 校验 scope；未登记路由默认拒绝。表结构见数据模型文档 §4.7 / §4.8。
- 身份与权限对应：`sub`（user_code）→ RBAC 角色 / 权限（V6.2 起无影子用户表）。
- **接口准入表化（V6.5）**：管理人员可在管理端「准入管理」页查看全部资源接口准入点（`iam_endpoint_policy`），覆盖准入要求或重置为扫描默认。

**服务间内部能力（不属对外分类）—— 面向认证中心（M2M，硬规则：`PORTAL_SERVICE_TOKEN` + client_id=`resource-server`）**

| 分类 | 能力 |
|------|------|
| 按人供给 | 按用户名返回角色编码（`ROLE_xxx`）与权限编码集合 |

- 调用路径：`/api/internal/user/{username}/roles`（认证中心 M2M，`resource-server`；硬规则，不经规则表/不经 `service-client-ids` 配置，见 21.5 决策 D6 / 开发规范 §4.3）。
- 用途：供认证中心签发 id_token 时注入 authorities；返回值**只含角色 / 权限编码，不含任何凭据**。
- **现状（2026-08）：已接线**——认证中心 `PortalUserDetailsService` → `RemoteRoleService.getUserRoles(userCode)` 按 user_code 取业务 RBAC（角色权威在资源中心），资源中心不可达时降级按 user_label 映射（`ADMIN_SERVICE_TOKEN` / `ROLE_USER`）并告警（对应原“改造清单 #17”，现已归档为已完成，见 `docs/改造清单-一级框架.md` §2）

**明确不对外提供**：健康检查（`/health` 已删除）、`oauth2_registered_client` 直接读取（目录数据改经认证中心目录 API，见 21.5 决策）、用户 / 客户端等身份库管理（归属认证中心）。

> **接口明细（端点 / 参数 / 调用示例）**：[对外接口说明 §2 资源中心](./对外接口说明.md#resource-center)

```
└───────────────────────────────────────────────────────────────────┘
```

> 备注：E ↔ F 之间的服务间 M2M（⑦）不经过浏览器，含资源中心 F 以 client_credentials 调认证中心 `/oauth2/token`、`/oauth2/introspect`、`/api/directory/clients`；认证中心 E 内部角色供给（`/api/internal/user/{username}/roles` → 9010，**硬规则**：`PORTAL_SERVICE_TOKEN` + client_id=`resource-server`）**已接线**（`PortalUserDetailsService`→`RemoteRoleService`，见 21.5 决策 D6）。

图例（数字对应能力归属矩阵 23.3 的说明列）：

- **①** 管理台页面经 C 透传调管理 API：用户 / 客户端 / 会话 / 授权记录 → 认证中心 9000；角色 / 权限 → 资源中心 9010。
- **②** 门户页面经 D 获取当前人员可见客户端（**portal 端能力**，→ 资源中心 9010 `/api/public/clients/mine`）。

- **⑤** 管理 API：`/api/admin/**`（用户 / 客户端 / 会话 / 授权记录）→ 9000，Bearer + `ADMIN_SERVICE_TOKEN`。
- **⑥** 角色 / 权限管理：`/api/admin/roles|permissions` → 9010，Bearer + `ADMIN_SERVICE_TOKEN`（经 C 透传）。
- **⑧** 业务系统 G 经各客户端模式向认证中心换取令牌（授权码 / 密码 / 设备码）。
- **⑨** 业务系统 G 携带用户 Bearer 调用资源中心 `/api/capability/contacts`、`/api/capability/contacts/{id}`（任意凭证 + 客户端能力订阅）。

> 服务间内部 → `controller/internal`。（分包规范 / 默认准入推导见 [`docs/开发规范.md`](./开发规范.md) §4.2）

### 23.4 决策与限制

> **开发规范统一见 [`docs/开发规范.md`](./开发规范.md)**（分包/能力域/凭证矩阵/用户生命周期边界）；本节仅保留决策结论，不复述规范细节。

- **认证中心不提供业务能力**：业务 / 公开 API 一律归资源中心（9000 仅认证 + 管理面）。
- **服务间默认 M2M**：跨服务调用统一走 client_credentials + introspection，不共享用户令牌（21.5 决策 D6）。
- **内部角色供给已接线**：`/api/internal/user/{username}/roles`（`controller/internal`）由认证中心 `PortalUserDetailsService`→`RemoteRoleService` 按 user_code 调用，id_token claims 来自资源中心 RBAC（不可达时降级 user_label 映射并告警）。
- **管理台角色管理走管理端能力**：管理台"按人查/分配角色"规划为 `/api/admin/...`（`ADMIN_SERVICE_TOKEN` + admin-app 白名单，`controller/admin`），不并入内部接口（`controller/internal` 仅只读内省，见开发规范 §4.3）。
- **管理面路径收敛**：`/api/admin/**` 在认证中心与资源中心均以 `ADMIN_SERVICE_TOKEN` 收口；admin-app 客户端白名单见 `authserver.admin-client-ids`；认证中心等以机器身份触发的管理写以**管理 M2M 服务凭证**（`admin-m2m`）注入（见开发规范 §5）。

## 24. 新服务接入指南（方案一：纯业务微服务）

> **重点：`/api/internal/**`（资源中心 `controller/internal`）是对标认证中心内省接口的存在，且为硬规则——仅认证中心 M2M（`resource-server`）可调，不进入 `iam_endpoint_policy` 规则表、不经 `service-client-ids` 配置、不可被管理端覆盖（V6.10 起）。**
> 身份 + 权限双内省链路依然是所有新服务鉴权的根基，但新服务的**权限获取通道收敛为认证中心内省**（认证中心内部已接线 `controller/internal` 角色内省），新服务不与资源中心 internal 直接对接。
> （`controller/internal` 仅只读、管理写归 `/api/admin/**` 等边界约定，见 [`docs/开发规范.md`](./开发规范.md) §4.3。）

### 24.1 内省接口对标：身份内省 vs 权限内省

| 维度 | 认证中心内省 | 资源中心内部接口（**认证中心专用**） |
|------|-------------|----------------------------------|
| 端点 | `POST /oauth2/introspect` | `GET /api/internal/user/{username}/roles` |
| 模块 | iam-authorization-server :9000 | iam-resource-service :9010（`controller/internal`） |
| 鉴权 | client_credentials（resource-server） | **硬规则**：`PORTAL_SERVICE_TOKEN` + client_id=`resource-server`（仅认证中心 M2M） |
| 输入 | access_token | username（token 内省后得 `sub`） |
| 输出 | 令牌有效、scope、`sub`、`client_id`、`grant_type`、令牌类别（ADMIN_SERVICE_TOKEN / ROLE_USER） | 业务角色 + 业务权限编码（ADMIN / USER / app:xxx），含 ADMIN 角色时注入 ADMIN_SERVICE_TOKEN |
| 职责 | **身份**校验：令牌是谁的、是否有效 | **权限**供给：这个人能做什么（RBAC，`iam_authorization`） |
| 对标关系 | = OAuth2 内省 | = **权限内省（认证中心的配套补齐，新服务不直连）** |

> 二者不可互替：认证中心只知道「token 有效 + 身份类型角色」；真正的业务级权限（`app:portal` 等）只存在于资源中心 RBAC。一个完整的授权判断 = 认证内省（验身份）+ 权限内省（取权限）。认证中心在登录/签发时把权限内省结果注入 id_token claims 供下游共享。

### 24.2 为什么单独成章、为什么要重点标记

- `controller/internal` 是**服务间能力**，不属于对外三分类（管理端 / portal 端 / 公开端），极易被忽略；
- 它是**认证中心专用**的取权限通道（硬规则，仅认证中心 M2M 可调）：认证中心登录/签发时经它取业务权限，并把结果注入 id_token claims，供下游新服务共享；
- 现状（2026-08）：接口**已接线**（认证中心 `PortalUserDetailsService`→`RemoteRoleService` 取业务权限注入 authorities）。**新服务不直接调用 internal**，其业务权限经认证中心内省/id_token claims 获取（见 24.4 第 4 步）。

### 24.3 方案一接入步骤（新服务 = 纯业务微服务）

**前提**：新服务有自己的业务库（**不写入 `iam_authorization`**，角色/权限中心与业务数据解耦）。

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 独立业务库 | 业务表放自己库，不扩 `iam_authorization` schema |
| 2 | 注册 OAuth2 client | 认证中心登记 client_id（client_credentials，M2M 或资源服务器内省用） |
| 3 | 配置 Resource Server | `introspection-uri → http://localhost:9000/oauth2/introspect`，携带 resource-server（或新 client）凭证 |
| 4 | **业务权限来源** | 新服务不做 RBAC 直查、不直连 `controller/internal`（硬规则仅认证中心）；取认证中心内省 / id_token claims 中已注入的业务角色与权限（`app:xxx`） |
| 5 | 方法级鉴权 | 业务方法用 `@PreAuthorize` / `hasAuthority('app:xxx')` / `hasRole('ROLE_xxx')` |
| 6 | 管理面（如需） | 若新服务需要管理接口，走管理端能力域 `/api/admin/**`（`ADMIN_SERVICE_TOKEN`） |

**最小接入代码示意（第 3-4 步）**

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        opaque-token:
          introspection-uri: http://localhost:9000/oauth2/introspect
          client-id: resource-server
          client-secret: 123456
```

```java
// 自定义 introspector：内省后从 id_token claims 提取业务权限（认证中心已接线 internal 角色内省注入）
public class BizAuthoritiesOpaqueTokenIntrospector implements OpaqueTokenIntrospector {
    // 1. delegate.introspect(token) → OAuth2AuthenticatedPrincipal（含 sub 与 roles claim）
    // 2. 将 attributes 中的 roles / permissions 合并进 authorities，返回新 principal
    // 3. 无需直连资源中心 internal（硬规则，仅认证中心 M2M 可调）
}
```

### 24.4 接入前需完成的演进（internal 从"建好"到"可用"）

| # | 事项 | 状态 |
|---|------|------|
| 1 | 认证中心登录时接线 `internal`，将权限注入 id_token claims（或直接供内省用） | ✅ 已接线（`PortalUserDetailsService`→`RemoteRoleService`，D6） |
| 2 | internal 鉴权收敛为 **硬规则**：仅认证中心 M2M（`resource-server`）可调，**不再**以 `service-client-ids` 白名单开放给各新业务服务 | ✅ 已落地（V6.10：`EndpointAdmissionManager` 前置裁决 + `EndpointPolicyService` 整域清理） |
| 3 | 明确权限语义：`iam_authorization` 角色/权限为业务级唯一权威；认证中心 `identity_type` 仅映射身份类型角色 | 待定 |
| 4 | 接口限流 / 内网隔离（R7 防枚举） | 建议 |

### 24.5 服务令牌判定实现（判据修正记录）

> 说明：上述演进项不进入本期改造清单，作为新服务接入的前置条件单独推进。判据修正已落地代码，记录如下。

**背景**：原 `RbacAuthoritiesOpaqueTokenIntrospector` 以「本地查不到用户 ⇔ 服务令牌」反推注入 `ROLE_SERVICE`。D9 同步未做时，仅存在于 `iam_identity` 的新用户会被误判为服务令牌 → 越权访问 `/api/internal/**` 且拿不到业务权限。

**修正**：服务令牌判定改为依据 token 自身属性，不依赖本地用户表。

| 判定来源 | 实现 |
|----------|------|
| 认证中心内省 | `EnrichedOAuth2TokenIntrospectionAuthenticationProvider` 在内省响应强制补 `grant_type`（authorization 的 AuthorizationGrantType）；认证中心自身 `/api/admin/**` 用 `RedisOpaqueTokenIntrospector`（同样补 `grant_type`） |
| 资源中心 introspector | `isServiceToken()`：`grant_type == client_credentials` **或** `client_id ∈ authserver.service-client-ids` → 注入 `PORTAL_SERVICE_TOKEN`（门户服务凭证）；用户令牌按 RBAC 解析，业务角色含 `ADMIN` 时注入 `ADMIN_SERVICE_TOKEN`（管理服务凭证），`client_id ∈ portal-client-ids`（门户应用客户端，如 portal-app）时额外注入 `PORTAL_SERVICE_TOKEN`，本地查不到用户时**不注入任何角色** |
| internal 路径 | **硬规则**：`EndpointAdmissionManager.check` 前置分支 `/api/internal/**` → `PORTAL_SERVICE_TOKEN` **且** client_id=`resource-server`（不经规则表、不经配置，V6.10） |
| portal 路径 | `EndpointAdmissionManager.clientWhitelistGate`：`PORTAL_SERVICE_TOKEN` **且** `client_id ∈ portal-client-ids`（门户客户端白名单，默认 portal-app） |
| 配置 | `application.yml → authserver.service-client-ids`（**已与 internal 解耦**，仅作服务令牌判定兜底）、`authserver.portal-client-ids`（默认 `[portal-app]`） |

**效果**：
- 新用户（未同步 D9）→ 用户令牌分支，本地无记录不注入角色 → 无业务权限、进不了 internal（不再是 `PORTAL_SERVICE_TOKEN`）。
- client_credentials 服务令牌 → 正常注入 `PORTAL_SERVICE_TOKEN`；但 **internal 域仍仅 `resource-server` 可调**（其它服务令牌即使持 `PORTAL_SERVICE_TOKEN` 也被硬规则拒绝）。
- portal 域 → 仅门户白名单客户端可访问，门户信息不对任意客户端开放。
- 未来对外 API 服务平台 → 业务权限经认证中心内省/id_token claims 获取，**无需也不被允许**直接调用 internal（V6.10 起）。
