# 权限架构改造 — 现状摸底与落地计划

> 摸底时间: 2026-10-22 (dev DB 实测 + 代码核查)。本文是权限改造阶段 0 的设计输入, 实施以本文数据为基线。

## 1. 背景与结论

**要解决的真实问题**: RBAC 不完整 — `User → Role → Permission` 到权限码就断了, 权限码与
URL 资源 (`iam_endpoint_policy`) 从未绑定; API 准入只认「管理面/门户面」两个类别粗档,
管理端做不到「HR 只能管用户、不能管角色」这类资源级细粒度授权。

**结论 (方案对比定稿)**:

- **过度设计 (弃)**: 「三类型字典表 admin-console/user-portal/third-party-app + required_authority
  改类型 key」— client 白名单维度现状已存在 (`EndpointAdmissionManager.clientWhitelistGate`),
  该方案只是重新包装已有机制, 且类型 key 占掉 required_authority 后, 资源级角色要求无处存放。
- **最小方案 (定)**: 补全 `Permission ↔ Resource` 绑定 — 权限码进 `required_authority`,
  裁决复用已有 `hasAuthority` 默认分支。**粗档 (类别标签) 与细档 (权限码) 两档并存**, 平滑迁移。
- client 维度: 维持现状白名单闸 (管理端 only admin-app, 门户 only portal-app)。
- CAPABILITY 能力订阅: 已决策**本期整体清理** (范围见 §4)。

## 2. 摸底数据 (2026-10-22 实测)

### 2.1 数据层 (dev DB)

| 表 | 现状 | 含义 |

## 3. 判定链终态设计

```
准入 = required_authority 比对 (两档并存, 单字段):
         粗档: PERMIT_ALL / AUTHENTICATED / ADMIN_SERVICE_TOKEN / PORTAL_SERVICE_TOKEN
         细档: 任意 sys_permission.code (type=api), default 分支 hasAuthority 比对
       AND client 白名单闸 (现状不动, 防「有角色但拿错 client 的令牌」)
```

- 粗档语义不变, 新播种端点先落粗档 (defaultAuthorityOf 不改), 人工细化改码 — 无回滚风险。
- 细粒度验收标准: 角色只授 `user:list` 的用户 → `GET /api/admin/users` 200, `POST` 403。
- 初始化 (防鸡生蛋): 权限码种子 + ADMIN 角色绑全集写入迁移 SQL (bootstrap)。

## 6. 待拍板决策点

1. 权限码粒度: 对象一码 (`user:manage`) vs 对象×动作 vs **读写两档** (`*:read`/`*:write`, 建议)。
2. 本期角色: 只 ADMIN 绑全集 (细分角色下期) vs 同时建细分角色种子。
3. 61 行: 一次全改细码 (建议) vs 核心端点先改分批。
4. CAPABILITY 清理: 先于权限码改造 (建议, 同区域代码) vs 同批。
