# 多租户多商户管理平台推荐总体架构

## 一、总体架构

```
                         用户
                          |
                    统一认证入口
                          |
                 +--------v---------+
                 |   Auth Center    |
                 | 认证中心         |
                 +--------+---------+
                          |
                    Access Token
                          |
        +-----------------+----------------+
        |                                  |
        v                                  v

+---------------+                 +----------------+
| Resource      |                 | Tenant Center |
| Center        |                 | 租户中心       |
| 授权中心       |                 | 商户中心       |
+---------------+                 +----------------+

        |
        |
        +----------------+
        |                |
        v                v

+---------------+     +----------------+
| Portal        |     | Open Platform |
| 门户中心       |     | 开放平台       |
+---------------+     +----------------+
```

## 二、核心设计思想

该平台不是单纯 IAM，而是多租户、多商户 SaaS 平台。

采用认证、租户、资源、门户、开放平台五中心协同模式。

## 三、各中心职责

### Auth Center（认证中心）

负责：

- 用户登录
- 密码认证
- OAuth2/OIDC
- Token
- Session
- SSO

数据库：

iam_auth_db

---

### Tenant Center（租户中心）

负责：

- 租户
- 商户
- 组织
- 部门
- 成员关系
- 租户配置
- 套餐

数据库：

iam_tenant_db

---

### Resource Center（资源中心）

负责：

- RBAC
- 角色
- 权限
- 资源
- 授权关系
- 数据权限

数据库：

iam_resource_db

---

### Portal Center（门户中心）

负责：

- 门户应用
- 工作台
- 菜单
- 页面
- 导航
- 组件配置

数据库：

portal_db

门户产生的菜单、页面等资源需要注册到 Resource Center。

---

### Open Platform（开放平台）

负责：

- 第三方应用
- API管理
- Client管理
- 密钥
- API订阅
- 调用统计

数据库：

open_platform_db

---

## 四、多租户权限模型

推荐模型：

```
租户
 |
组织
 |
用户
 |
角色
 |
权限
 |
资源
```

权限不能简单设计为：

用户 -> 角色 -> 权限

必须带租户隔离。

## 五、数据库划分与表清单

### 5.1 盘点口径与当前现状

本章以当前项目的基线 SQL、增量迁移、实体映射和已接通的管理功能为准，盘点日期为 2026-08-18。

当前项目实际只有两个物理数据库：

| 当前物理库 | 表数量 | 当前职责 |
|---|---:|---|
| `iam_identity` | 8 | 用户凭据、OAuth2/OIDC、租户目录、客户端准入 |
| `iam_authorization` | 11 | RBAC、应用目录、组织、接口准入、开放能力 |

第 5 章中的 `iam_auth_db`、`iam_tenant_db`、`iam_resource_db`、`iam_portal_db`、`iam_open_db` 是推荐的目标领域库，不是当前已经完成的物理分库。现有 19 张表按目标领域重新归类如下：

| 目标领域库 | 已有表数量 | 当前物理位置 | 结论 |
|---|---:|---|---|
| `iam_auth_db` | 6 | `iam_identity` | 认证主链路已具备，安全治理和持久化仍需补强 |
| `iam_tenant_db` | 3 | `iam_identity` 2 张、`iam_authorization` 1 张 | 只有租户和基础组织目录，还不是多商户中心 |
| `iam_resource_db` | 6 | `iam_authorization` | 简单 RBAC 可用，但角色分配尚未按租户隔离 |
| `iam_portal_db` | 2 | `iam_authorization` | 已有应用卡片和渠道，尚无菜单、页面、工作台配置 |
| `iam_open_db` | 2 | `iam_authorization` | 能力登记和订阅可用，尚无开发者、第三方应用和调用计量 |

状态说明：

- **已实现**：已有表、实体和业务读写链路，能够支撑当前功能。
- **部分实现**：表已使用，但缺少完整业务闭环或多租户约束。
- **仅建表**：已有表结构，业务逻辑尚未接入。
- **待新增**：当前项目没有该表。
- **待改造**：不是新增表，而是现有表必须增加租户维度或调整唯一约束。

### 5.2 `iam_auth_db`：认证中心

#### 已有表

| 表名 | 当前状态 | 用途 |
|---|---|---|
| `sys_user` | 已实现 | 用户凭据主表，保存 `user_code`、用户名、BCrypt 密码、账号启用/锁定/过期状态和基础资料 |
| `iam_external_identity` | 仅建表 | 微信、企业微信、钉钉、支付宝、Google、GitHub 等外部身份与本地 `user_code` 的绑定关系；绑定、解绑和第三方登录尚未接通 |
| `oauth2_registered_client` | 已实现 | OAuth2 客户端注册、授权模式、回调地址、Scope、Token 设置和 BCrypt 客户端密钥 |
| `oauth2_authorization_consent` | 已实现 | 用户对客户端的 OAuth2 授权同意 |
| `oauth2_authorization_record` | 已实现 | 授权历史及撤销记录；这是审计历史，不是运行时 Token 状态表 |
| `iam_client_policy` | 已实现 | 客户端登录边界策略，例如 `admin-app` 仅允许 `ADMIN`、`portal-app` 仅允许 `USER` |

#### 还需要增加的表

| 建议表名 | 优先级 | 用途 |
|---|---|---|
| `iam_login_attempt` | P0 | 记录登录失败、来源 IP、客户端、失败原因、锁定截止时间，支撑防爆破、限流和账号解锁 |
| `iam_password_history` | P1 | 保存历史密码摘要，支撑密码过期、禁止复用和密码策略 |
| `iam_operation_audit` | P0 | 记录用户、客户端、租户、角色、策略等敏感管理操作的操作者、对象、前后值和结果；后续规模扩大可独立为审计库 |
| `oauth2_authorization` | P2/按需 | 将授权码、Access Token、Refresh Token、Device Code 等运行时授权从仅 Redis 升级为 JDBC 真源；当前 Redis 方案可继续运行 |
| `spring_session` | P2/按需 | 持久化 SSO HttpSession，提高 Redis 重启后的会话恢复能力 |
| `spring_session_attributes` | P2/按需 | 保存 `spring_session` 对应的会话属性 |

认证中心继续作为客户端密钥的唯一权威。其他库只能保存 `client_id`，不得复制客户端明文或密文密钥。

### 5.3 `iam_tenant_db`：租户与商户中心

#### 已有表

| 表名 | 当前物理位置 | 当前状态 | 用途 |
|---|---|---|---|
| `iam_tenant` | `iam_identity` | 已实现 | 租户目录，支持租户增删改查和启停 |
| `iam_tenant_user` | `iam_identity` | 已实现 | 用户与租户的成员关系，支持一人属于多个租户 |
| `iam_org` | `iam_authorization` | 部分实现 | 集团、公司、部门等组织树节点；当前只有表、实体和授权主体校验，没有组织管理 API、页面及人员归属 |

`iam_org` 推荐迁入 `iam_tenant_db`。组织是租户主数据，不应由资源中心长期维护。

#### 还需要增加的表

| 建议表名 | 优先级 | 用途 |
|---|---|---|
| `iam_merchant` | P0 | 租户下的商户/经营主体，一租户可包含多个商户；保存商户编码、名称、类型、上级商户、状态和结算主体等基础信息 |
| `iam_merchant_user` | P0 | 用户与商户的成员关系，解决用户可进入哪些商户、在商户内是否启用的问题 |
| `iam_org_user` | P0 | 用户与组织/部门的归属关系，支持主部门、兼职部门、职位和任职状态，也是 `ORG` 授权真正生效的前提 |
| `iam_tenant_config` | P1 | 租户级配置，例如品牌、域名、时区、语言、登录策略、默认商户和功能开关 |
| `iam_package` | P1 | SaaS 套餐定义，例如基础版、专业版、企业版及状态 |
| `iam_package_feature` | P1 | 套餐包含的功能、资源、容量和配额，可关联资源中心的资源编码 |
| `iam_tenant_package` | P1 | 租户订购套餐的生效时间、到期时间、状态和覆盖配置 |

商户与组织不能混为一张表：商户是经营和数据归属主体，组织是行政/人员树。业务表通常同时携带 `tenant_code` 和 `merchant_code`，人员权限再通过组织、角色和数据范围计算。

### 5.4 `iam_resource_db`：资源与授权中心

#### 已有表

| 表名 | 当前状态 | 用途 |
|---|---|---|
| `sys_role` | 部分实现 | 角色定义；当前 `ADMIN`、`USER` 等角色是全局角色，没有租户维度 |
| `sys_permission` | 部分实现 | 权限点定义；当前主要是 `app:xxx` 应用访问权限，尚未形成统一资源模型 |
| `sys_role_permission` | 已实现 | 角色与权限关联 |
| `sys_user_role` | 部分实现 | 用户与角色关联；当前只有 `user_code + role_id`，同一用户在不同租户中的角色无法区分 |
| `iam_app_authorization` | 部分实现 | 应用对 `ROLE`、`USER`、`ORG` 三类主体授权；`ROLE/USER` 已生效，`ORG` 因缺少 `iam_org_user` 尚不能解析 |
| `iam_endpoint_policy` | 已实现 | 资源接口准入策略，由启动扫描播种并允许管理端覆盖；未登记路径默认拒绝 |

#### 现有表必须改造

| 表名 | 必须改造内容 | 原因 |
|---|---|---|
| `sys_role` | 增加角色作用域和 `tenant_code`；租户角色编码按租户唯一，平台内置角色单独标识 | 当前角色全局共享，不符合租户级 RBAC |
| `sys_user_role` | 增加 `tenant_code`，唯一约束调整为租户、用户、角色组合 | 同一用户在不同租户可拥有不同角色 |
| `iam_app_authorization` | 所有查询强制按当前 `tenant_code` 过滤，并校验应用、主体与授权记录属于同一租户 | 防止跨租户授权和越权读取 |
| `sys_permission` | 明确平台公共权限与租户自定义权限边界；允许租户自定义时增加 `tenant_code` | 防止租户自定义权限编码冲突 |

#### 还需要增加的表

| 建议表名 | 优先级 | 用途 |
|---|---|---|
| `iam_resource` | P0 | 统一登记应用、菜单、页面、按钮、API、数据对象等资源，保存资源类型、归属服务、业务编码和租户范围 |
| `iam_permission_resource` | P0 | 建立权限点与资源/动作的关系，使“权限”不再只等同于应用编码 |
| `iam_data_scope` | P0 | 定义本人、本部门、部门及子级、指定组织、指定商户、自定义条件等数据权限规则 |
| `iam_role_data_scope` | P0 | 将角色绑定到数据权限规则，供资源访问时计算数据过滤范围 |

门户中心和开放平台负责创建自身资源，资源中心只维护资源登记、权限和授权关系。

### 5.5 `iam_portal_db`：门户中心

#### 已有表

| 表名 | 当前物理位置 | 当前状态 | 用途 |
|---|---|---|---|
| `iam_application` | `iam_authorization` | 已实现 | 门户应用卡片，包含租户、应用编码、名称、图标、排序、可见性和状态 |
| `iam_application_channel` | `iam_authorization` | 部分实现 | 应用的 Web、Mobile 等渠道及 SSO `client_id` 绑定；渠道密钥创建/重置的一次性展示流程尚未接通 |

这两张表推荐迁入 `iam_portal_db`。`iam_app_authorization` 仍归资源中心，通过应用编码或资源编码关联，不复制门户配置。

#### 还需要增加的表

| 建议表名 | 优先级 | 用途 |
|---|---|---|
| `iam_portal_menu` | P1 | 租户/应用下的树形菜单和导航，关联页面及资源中心权限编码 |
| `iam_portal_page` | P1 | 页面注册、路由、页面类型、所属应用和启停状态 |
| `iam_portal_component` | P1 | 工作台组件定义、组件类型、数据源和默认配置 |
| `iam_portal_workspace` | P1 | 租户、角色或用户使用的工作台方案及布局版本 |
| `iam_portal_workspace_item` | P1 | 工作台中的组件实例、位置、尺寸和个性化配置 |
| `iam_portal_user_preference` | P2 | 用户收藏、常用应用、应用排序、默认工作台等个人偏好 |

菜单、页面和组件发布时，应将可授权对象注册为 `iam_resource`，再由资源中心完成角色授权。

### 5.6 `iam_open_db`：开放平台

#### 已有表

| 表名 | 当前物理位置 | 当前状态 | 用途 |
|---|---|---|---|
| `iam_api_capability` | `iam_authorization` | 已实现 | 开放 API 能力登记，包含路由、Scope、归属方和声明式 QPS 上限 |
| `iam_capability_subscription` | `iam_authorization` | 部分实现 | 客户端订阅能力及有效期、QPS、日/月配额；订阅准入已生效，但限流和配额尚未真实计数 |

这两张表推荐迁入 `iam_open_db`，资源服务在请求准入时通过开放平台 API 或缓存读取能力和订阅结果。

#### 还需要增加的表

| 建议表名 | 优先级 | 用途 |
|---|---|---|
| `iam_open_developer` | P1 | 开发者、开发团队、联系人、认证状态和所属租户 |
| `iam_open_application` | P1 | 第三方应用主体，保存应用所有者、用途、环境、审核和上下架状态 |
| `iam_open_app_client` | P1 | 第三方应用与认证中心 `client_id` 的映射；只存客户端标识和环境，不保存密钥 |
| `iam_capability_subscription_apply` | P1 | API 订阅申请、审批意见、审批人和状态流转历史 |
| `iam_capability_usage` | P0 | 按客户端、能力、租户和时间窗口聚合调用次数，用于 QPS、日配额和月配额执行 |
| `iam_api_call_log` | P1 | API 调用明细、耗时、状态码、错误码和追踪 ID，用于审计、问题定位和统计回溯 |

`oauth2_registered_client` 仍归认证中心。开放平台管理第三方应用和 `client_id` 的业务关系，密钥签发、重置和校验统一调用认证中心。

### 5.7 当前必须优先解决的问题

1. **租户上下文未闭环**：当前 `sys_role`、`sys_user_role` 没有租户维度，资源中心的应用和开放能力代码还存在固定 `T001` 默认值。上线多租户前必须由登录选择、Token 声明或可信请求上下文确定当前租户，并在所有查询中强制过滤。
2. **多商户尚未建模**：当前没有商户表、商户成员关系和 `merchant_code` 数据隔离，不能称为多商户平台。
3. **组织授权尚未闭环**：`iam_app_authorization` 可以保存 `ORG`，但没有 `iam_org_user`，门户查询也暂不匹配组织主体。
4. **资源和数据权限尚未落地**：当前权限主要表示应用访问，没有菜单、按钮、API、数据对象资源，也没有数据范围规则。
5. **门户仍是应用卡片层级**：已有应用和渠道管理，但没有菜单、页面、组件和工作台配置。
6. **开放平台仍是管理端登记模式**：已有能力与订阅，但没有开发者自服务、第三方应用审核、调用计量和调用审计。

### 5.8 推荐建设顺序

| 阶段 | 建设内容 | 完成标志 |
|---|---|---|
| P0 | 租户上下文、租户级角色、商户及成员、组织成员、统一资源、数据权限、调用计量、管理审计 | 数据和授权不能跨租户/商户，`ORG` 授权和配额真正生效 |
| P1 | 物理拆分 Tenant/Portal/Open 数据、套餐、门户配置、开发者与第三方应用、订阅审批、调用日志 | 五个中心形成清晰的数据所有权和服务 API |
| P2 | 用户偏好、密码历史、OAuth2/Session JDBC 持久化、统计归档 | 完成体验增强、恢复能力和长期运营能力 |

不建议一次性将 19 张表直接搬到五个库。应先补齐租户语义和服务 API，再按“新库双写/回填校验/切读/停止旧写”的顺序迁移，跨库关联继续使用 `user_code`、`tenant_code`、`merchant_code`、`org_code`、`client_id` 等业务编码，不建立跨库外键。

## 六、最终服务结构

```
IAM Platform

├── Auth Center
├── Tenant Center
├── Resource Center
├── Portal Center
└── Open Platform
```

## 七、核心原则

- 租户决定“你属于谁”
- 认证决定“你是谁”
- 资源中心决定“你能干什么”
- 门户决定“你看到什么”
- 开放平台决定“别人如何接入”

资源由所属中心注册，授权中心管理授权关系。
