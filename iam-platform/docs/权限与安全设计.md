# 权限与安全设计

平台的授权模型是**双维正交**的：用户维度（细粒度，角色→权限码）与客户端维度（粗粒度，scope→权限码）**收敛到同一张 `sys_permission` 字典后取交集**，全程 fail-closed。

> 核心公式：**令牌业务权限码 = 用户 RBAC 码 ∩ 客户端 scope 展开码**

---

## 一、四层裁决链

```text
① 签发准入   /oauth2/authorize    用户码 ∩ 客户端scope码 为空 → 拒发码 → /login.html?error=access_denied
② 令牌自省   自省器注入            用户码 ∩ 客户端scope码 = 令牌实际业务权限码
③ 端点准入   iam_endpoint_policy  请求(方法+路径) → 所需权限码 ∈ 令牌码 才放行
④ 认证档     表外三前缀端点       持有效内省令牌即放行；/permitall/** 链层直接放行
```

任一层缺口 → 拒绝（403 / 拒发码 / 拒绝签发），**无猜测放行路径**。

### ① 签发准入（混合登录隔离）

`IssuanceAdmissionService` + `AuthorizeIssuanceFilter`（挂 `/oauth2/authorize`）：

```
scopeCodes = 展开该客户端持有的 scope → 权限码
若 scopeCodes 为空（纯 OIDC 客户端）        → 放行（其令牌自省层同样拿不到业务码）
否则 userCodes ∩ scopeCodes 为空           → 拒发码，302 → 登录页显示「当前账号无权登录该应用」
```

**效果**：`user`（PORTAL 角色）登 `admin-app` 被拒；`admin`（ADMIN 角色）登 `portal-app` 被拒。
与②**读同一套 scope 字典、用同一条语义**，不新建规则表（旧 `iam_client_policy` 已退役）。

### ② 令牌自省（双维交集）

`RbacAuthoritiesOpaqueTokenIntrospector`：

```java
roleCodes   = sub(user_code) → sys_user_role → sys_role                    // 业务角色，原样注入
userCodes   = sub            → sys_user_role → sys_role → sys_role_permission → sys_permission(启用)
scopeCodes  = client_id      → registered_client.scopes → sys_scope(启用) → sys_scope_permission → sys_permission(启用)
注入的业务码 = userCodes ∩ scopeCodes                                        // fail-closed
```

- 用户有码、客户端 scope 未含 → 不注入（403）
- 客户端有 scope、用户无码 → 不注入（403）
- 客户端无业务 scope → 一码不放

### ③ 端点准入

`EndpointAdmissionManager`（`AuthorizationManager`）：

| 情况 | 裁决 |
|---|---|
| `required_authority = PERMIT_ALL` | 放行 |
| `required_authority = AUTHENTICATED` | 持有效令牌即放行 |
| `required_authority = <权限码>` | 令牌 authorities 含该码才放行 |
| `status = 0`（停用行） | 直接拒绝 |
| 表外路径 | 认证档（有效内省令牌） |

## 二、权限码字典（17 码，`sys_permission`）

| 域 | 码 | 数量 |
|---|---|---|
| 管理端 | `user/role/session/application/client/permission/record/policy` 各 `:read`/`:write` | **16** |
| 门户 | `portal:client:read` | **1** |

> 业务分类由 `remark` 前缀 `【管理端】`/`【门户】` 标记（无 domain 列）。

---

## 三、客户端授权范围（3 组，`sys_scope`）

| scope | 展开码 | 持有客户端 | 展开后 |
|---|---|---|---|
| `admin.full` | 16 个 admin 域码 | `admin-app` | 管理后台全量能力 |
| `portal.profile` | `portal:client:read` | `portal-app` | 门户「我的应用授权」 |
| `third.profile` | **空** | `web-app` | 0 业务码，仅 OIDC 标准端点 |

**域内自洽**：scope 的域由 `code` 前缀表达（`admin.`/`portal.`/`third.`），映射的码必须与之同域——
`admin.full` 只能绑 admin 域码、`portal.profile` 只能绑 portal 域码。这是混合登录隔离的根因。

---

## 四、角色绑定现状（`sys_role_permission`）

| 角色 | 绑定码 | 说明 |
|---|---|---|
| `ADMIN` | 16（admin 域全量） | 管理后台运营者 |
| `PORTAL` | 1（`portal:client:read`） | 门户用户 |
| `THIRD_PARTY` | 0 | 三方用户，暂无能力 |

---

## 五、端点准入表（`iam_endpoint_policy`，48 行）

- 每行 = 一个接口准入点（`method + path` 唯一），`required_authority` 填权限码
- **写入方**：`sql/iam.sql` 种子（精确码权威）+ 启动自扫描补缺（只补新端点，不回写、不剪除）
- **页面只读**，无增删改；停用行 = 该端点直接拒绝
- 控制器方法须位于 `controller.admin|biz` 包下才会被扫描入表，否则落认证档

## 六、一次请求的完整判定示例

```
admin 用户经 admin-app 调 GET /admin/users
  ① 签发: admin 有 16 码 ∩ admin.full(16码) = 非空 → 发码
  ② 自省: 注入 {ADMIN} + 16 个业务码
  ③ 准入: 路径命中 GET /admin/users → required_authority=user:read
          user:read ∈ 令牌码 → 放行 ✓

user (PORTAL) 经 admin-app 调 GET /admin/users
  ① 签发: user 有 {portal:client:read} ∩ admin.full(16 admin码) = ∅ → 拒发码 → 登录页越权提示 ✗
```

## 七、设计裁定

1. **fail-closed 是默认姿态**：签发、自省、端点准入三层任一缺口即拒绝。
2. **双维正交、单一轮词**：两侧都以 `sys_permission.code` 为共同货币，交集是朴素集合运算；不引入第二套权威。
3. **权限码即稳定标识**：`required_authority` 按字符串引用 `code`，**无外键无写时强校验**——重命名码会让引用行静默失联，因此码一经发布即不可改名（只能停用后新建）。
4. **字典演进走 SQL 种子**：`sys_scope` 一族不提供页面写入口，避免"页面"与"种子"双演进路径打架。

## 八、已退役机制（勿再引用）

| 机制 | 退役原因 | 接替者 |
|---|---|---|
| `iam_client_policy`（登录边界策略） | 与 scope 语义重复的第二权威，fail-open | ①签发准入（fail-closed，同源 scope） |
| `AuthServerProperties` + `admin/portal-client-ids` 白名单闸 | scope 分区后冗余 | ①② 的双维交集承担客户端隔离 |
| `ADMIN_SERVICE_TOKEN` / `PORTAL_SERVICE_TOKEN` 粗档常量 | 多态软关联字段，易产生静默死行 | 17 个细粒度权限码 |
| M2M / `client_credentials` 服务令牌分支 | 无消费方 | 按需以 `m2m.*` scope 重建 |
| `sys_user.user_label` 标签列 | 职责已被角色体系完全接管 | `sys_role` |
| `EndpointAdmissionManager` 客户端白名单 | 与 scope 分区重复 | 同上 |
