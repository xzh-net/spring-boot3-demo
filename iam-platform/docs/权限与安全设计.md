# 权限与安全设计

平台的授权模型分两层，全程 fail-closed：

- **登录层（①签发准入）**：`client_login_policy` 准入表裁决「谁能否登录哪个客户端」（allow-list），与权限码无关 —— 见 §二①；
- **授权层（②自省交集）**：用户维度（细粒度，角色→权限码）与客户端维度（粗粒度，scope→权限码）**收敛到同一张 `sys_permission` 字典后取交集**，决定令牌携带哪些业务码。

> 核心公式（授权层）：**令牌业务权限码 = 用户 RBAC 码 ∩ 客户端 scope 展开码**
> 两层解耦：改权限码不影响登录边界，改准入表不影响令牌业务码。

---

## 一、四层裁决链

```text
① 签发准入   /oauth2/authorize    client_login_policy 准入表未命中 → 拒发码 → /login.html?error=access_denied
② 令牌自省   自省器注入            用户码 ∩ 客户端scope码 = 令牌实际业务权限码
③ 端点准入   iam_endpoint  请求(方法+路径) → 所需权限码 ∈ 令牌码 才放行
④ 认证档     表外三前缀端点       持有效内省令牌即放行；/permitall/** 链层直接放行
```

任一层缺口 → 拒绝（403 / 拒发码 / 拒绝签发），**无猜测放行路径**。

### ① 签发准入（登录隔离，登录维度）

`LoginAdmissionService` + `AuthorizeIssuanceFilter`（挂 `/oauth2/authorize`）—— 查 **`client_login_policy` 准入表**（allow-list，fail-closed）：

```
无启用行 / 主体未命中  → 拒发码，302 → 登录页显示「当前账号无权登录该应用」
命中（ANY / ROLE 命中 / USER 命中）→ 放行，继续发授权码
```

**与②解耦**：登录资格只看准入表，不再由权限码交集推导 —— 改权限码不影响登录边界。
种子：`admin-app`←ROLE ADMIN、`portal-app`←ROLE PORTAL、`device-app`←ROLE THIRD_PARTY、
`oa-web-app`/`oa-h5-app`/`mobile-app`←ANY。「客户端管理 → 登录准入」分区维护（`/admin/login-policies`）。

### ② 令牌自省（双维交集）

`RbacAuthoritiesOpaqueTokenIntrospector`：

```java
roleCodes   = sub(user_code) → sys_user_role → sys_role                    // 业务角色，原样注入
userCodes   = sub            → sys_user_role → sys_role → sys_role_permission → sys_permission(启用)
scopeCodes  = client_id      → registered_client.scopes → sys_scope(启用) → sys_scope_permission → sys_permission(启用)
注入的业务码 = userCodes ∩ scopeCodes                                        // fail-closed
```

- 用户有码、客户端 scope 未含 → 不注入（403）
- 客户端有 scope、用户无码 → 不注入（403）
- 客户端无业务 scope → 一码不放

### ③ 端点准入

`EndpointAdmissionManager`（`AuthorizationManager`）：

| 情况 | 裁决 |
|---|---|
| `policy_type = PERMIT_ALL` | 放行 |
| `policy_type = AUTHENTICATED` | 持有效令牌即放行 |
| `policy_type = PERMISSION` | 令牌须满足权限码组合：`permission_logic=ALL` 全部具备 / `ANY` 命中其一 |
| `status = 0`（停用行） | 直接拒绝 |
| 绑定缺失 / 权限不可解析 | 拒绝（每请求 Fail-Closed） |
| 表外路径 | 认证档（有效内省令牌） |

## 二、权限码字典（17 码，`sys_permission`）

| 域 | 码 | 数量 |
|---|---|---|
| 管理端 | `user/role/session/application/client/permission/record/policy` 各 `:read`/`:write` | **16** |
| 门户 | `portal:client:read` | **1** |

> 业务分类由 `remark` 前缀 `【管理端】`/`【门户】` 标记（无 domain 列）。

## 三、客户端授权范围（`sys_scope` 6 行）

| scope | 类型 | 展开码 | 持有客户端 |
|---|---|---|---|
| `admin.full` | 业务组 | admin 域全量 | `admin-app` |
| `portal.profile` | 业务组 | `portal:client:read` | `portal-app` |
| `third.profile` | 业务组 | **空**（fail-closed） | `oa-web-app` / `oa-h5-app` |
| `openid` | 标准协议 | **空**（无映射；驱动签发 id_token） | 各客户端 |
| `profile` | 标准协议 | **空**（无映射；驱动 `/userinfo` 昵称/头像） | 各客户端 |
| `email` | 标准协议 | **空**（无映射；驱动 `/userinfo` 邮箱） | 除 `admin-app` 外均持有 |

> 标准协议三行零映射 → 展开为空，**不参与业务码**；入字典仅为客户端管理页勾选统一字典驱动（勾选什么就是什么）。`read`/`write` 为纯占位、不入字典（存量注册值保留，页面编辑时动态补框）。
> **remark 约定**：可写谁持有，不写数量。

**域内自洽**：业务组的域由 `code` 前缀表达（`admin.`/`portal.`/`third.`），映射的码必须与之同域——
`admin.full` 只能绑 admin 域码、`portal.profile` 只能绑 portal 域码。这是**授权层**（令牌业务码）的隔离基础；
**登录层**的混合登录隔离由 `client_login_policy` 准入表独立承担（见 §二①），两层各司其职。

## 五、端点准入（`iam_endpoint` 资源行 56 + `iam_endpoint_permission` 绑定 56）

- 每行 = 一个接口准入点（`method + path` 唯一，拆表后资源行不含权限码）
- `policy_type = PERMISSION` 的行经绑定表挂 1..N 个权限码，`permission_logic` 组合裁决（ALL=同时具备 / ANY=任一即可）；档位行（AUTHENTICATED/PERMIT_ALL）无绑定
- **写入通道**：种子一次性初始化 + 管理页面维护；资源与绑定两表同一事务提交；绑定表 `permission_id` 稳定引用 + FK RESTRICT，规则每请求直查 DB（改码零窗口），每请求 Fail-Closed（查询/绑定/解析失败一律拒绝），启动仅打漂移告警
- 停用行 = 该端点直接拒绝
- 控制器方法须位于 `controller.admin|biz` 包下才会被扫描入表，否则落认证档

## 六、一次请求的完整判定示例

```
admin 用户经 admin-app 调 GET /admin/users
  ① 签发: admin 有 16 码 ∩ admin.full(16码) = 非空 → 发码
  ② 自省: 注入 {ADMIN} + 16 个业务码
  ③ 准入: 路径命中 GET /admin/users → 绑定表给出所需码 [user:read] (ALL)
          user:read ∈ 令牌码 → 放行 ✓

user (PORTAL) 经 admin-app 调 GET /admin/users
  ① 签发: user 有 {portal:client:read} ∩ admin.full(16 admin码) = ∅ → 拒发码 → 登录页越权提示 ✗
```

## 七、设计裁定

1. **fail-closed 是默认姿态**：签发、自省、端点准入三层任一缺口即拒绝。
2. **双维正交、单一轮词（授权层）**：两侧都以 `sys_permission.code` 为共同货币，交集是朴素集合运算；不引入第二套权威。登录层独立于本公式（`client_login_policy` 准入表），改权限码不影响登录边界。
3. **权限码即稳定标识**：`iam_endpoint_permission.permission_id` 按 id 稳定引用（FK `ON DELETE RESTRICT`，改名自动跟随、被绑权限禁删，应用双守卫 + 数据库兜底）；`sys_scope_permission` 同理。码改名不影响引用行。
4. **字典演进走 SQL 种子**：`sys_scope` 一族不提供页面写入口，避免"页面"与"种子"双演进路径打架。

## 八、已退役机制（勿再引用）

| 机制 | 退役原因 | 接替者 |
|---|---|---|
| `iam_client_policy`（登录边界策略） | 与 scope 语义重复的第二权威，fail-open | ①签发准入（fail-closed，`client_login_policy` 准入表） |
| `AuthServerProperties` + `admin/portal-client-ids` 白名单闸 | scope 分区后冗余 | ①② 的双维交集承担客户端隔离 |
| `ADMIN_SERVICE_TOKEN` / `PORTAL_SERVICE_TOKEN` 粗档常量 | 多态软关联字段，易产生静默死行 | 17 个细粒度权限码 |
| M2M / `client_credentials` 服务令牌分支 | 无消费方 | 按需以 `m2m.*` scope 重建 |
| `sys_user.user_label` 标签列 | 职责已被角色体系完全接管 | `sys_role` |
| `EndpointAdmissionManager` 客户端白名单 | 与 scope 分区重复 | 同上 |
