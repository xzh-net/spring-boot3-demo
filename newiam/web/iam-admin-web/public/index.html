二、OIDC 令牌分工与 openid 使用

OAuth2 有 access_token 和 refresh_token，OIDC 在此基础上增加了 id_token。三者职责严格分离：

令牌 用途 消费者 典型 Claims 不应包含
id_token JWT 证明用户身份（Authentication） 客户端应用 sub, preferred_username, roles, iss, aud(=client_id), exp 资源标识(contacts-api)
access_token JWT 调用资源凭证（Authorization） 资源服务器 sub, roles, aud(=contacts-api), scope, exp preferred_username 等身份声明
refresh_token 续签 access_token 授权服务器 token 端点 opaque（不透明） 不应传给资源服务器

令牌获取与使用流程：

客户端
→
授权服务器
→
资源服务器
  • ① 授权阶段：客户端请求 scope=openid profile read write → 授权服务器返回 code
  • ② 换 token：客户端用 code 换 token → 响应同时包含 access_token、id_token、refresh_token
  • ③ 识别用户：客户端解析 id_token 的 JWT payload 获取 preferred_username、roles 等身份信息，建立本地会话
  • ④ 调 API：客户端用 access_token 作为 Bearer Token 调用 /api/**、/userinfo 等受保护资源
常见误用：从 access_token 解码用户身份信息 → 这是错误的。access_token 的 aud 是 contacts-api（资源标识），不是客户端标识。 正确做法是从 id_token 解码身份，用 access_token 调 API。

openid scope 使用示例：

// 授权请求时必须带 openid
GET /oauth2/authorize?response_type=code&client_id=web-app
    &redirect_uri=http://localhost:8300/callback
    &scope=openid profile email read write   ← openid 必须在此处
    &state=demo

// token 响应中会多出 id_token 字段
{
  "access_token": "eyJraWQ...",
  "id_token":     "eyJraWQ...",   ← 仅当 scope 含 openid 时返回
  "refresh_token": "eyJraWQ...",
  "token_type": "Bearer",
  "expires_in": 7200
}

三、为什么 access_token 用 Opaque，id_token 必须用 JWT

本系统采用 access_token = Opaque 引用令牌、id_token = JWT 自包含令牌 的组合策略。这是 OAuth2/OIDC 标准下经过权衡的最优选择，并非随手而为。

一、id_token 为什么必须是 JWT（OIDC 规范硬性要求）

  • 规范要求：OIDC Core 1.0 §2 明确规定 id_token 必须是 JWT 格式。若改成 opaque，就不再是 OIDC，只是普通 OAuth2。
  • 客户端本地解码：客户端拿到 id_token 后无需联网即可解码出 preferred_username、roles、iss、aud、exp 等身份声明，立即建立本地会话。若用 opaque，每次显示用户名都得调 /userinfo，违反 OIDC 设计初衷。
  • 签名可验证：JWT 带授权服务器签名，客户端可用公钥验签，防止 token 被伪造。
  • 一次性消费：id_token 仅在登录时使用一次（解码取身份），用完即弃。后续业务请求不带 id_token，不会带来体积或传输开销。
结论：id_token 是"身份证明"，用 JWT 是为了让客户端零网络开销拿到身份信息。

二、access_token 为什么不用 JWT 而用 Opaque

表面看 JWT 也能做 access_token（Google/GitHub 就是这么做的），但在本项目架构下用 JWT 不划算。逐条分析 JWT 的三大优势是否成立：

JWT 的理论优势 在本项目是否成立 原因
① 无状态（本地验签，零 IO） 不成立 需要主动撤销（强制下线/退出），已实现 JwtDenylistValidator 每请求查 Redis 黑名单 —— 无状态优势被抵消
② payload 可读，资源服务器直接拿 claims 不成立 客户端不解析 access_token；资源服务器只验签 + 查黑名单，没人消费 payload
③ 故障隔离（Redis 挂了仍可用） 半成立 Redis 挂了黑名单也挂了，撤销功能失效，安全性归零

JWT 的优势都不成立，但缺点却真实存在：

  • 体积大：JWT 约 1200 字节，Opaque 仅 32 字节，相差 37 倍。移动端弱网、HTTP 头部限制场景下明显劣势。
  • 信息泄露：JWT 的 payload 是 base64，任何人拿到 token 都能解码出 sub、roles、aud。Opaque 是随机串，无信息可泄露。
  • 撤销复杂：需要额外维护 oauth2:denylist: 黑名单 + sha256 计算 + TTL 管理。Opaque 直接删 Redis key 即可，原生支持。
核心洞察：JWT 的设计初衷是"让资源服务器不用查存储"，但只要业务需要主动撤销，资源服务器就必须查存储（黑名单）。此时 JWT 就退化成"带着多余 payload 的 opaque token"——缺点还在，优势没了。
既然资源服务器总要查存储，那 token 就应该是最薄的引用，而不是"自包含的大对象"。这正是 Okta、Auth0 等主流方案默认用 opaque 的根本原因。

三、Opaque 模式的工作原理

// 1. 客户端拿到的 access_token 是随机短码
{
  "access_token":  "a1b2c3d4e5f67890abcdef1234567890",   ← 32 字符随机串
  "id_token":      "eyJraWQ...",                          ← JWT 不变
  "refresh_token": "b2c3d4e5...",                          ← opaque
  "token_type":    "Bearer",
  "expires_in":    7200
}

// 2. 调 API 时原样转发 (客户端不关心格式, 业务 API 在独立资源服务 :9010)
GET http://localhost:9010/api/contacts
Authorization: Bearer a1b2c3d4e5f67890abcdef1234567890

// 3. 资源服务器查 Redis 验证 (或经 /oauth2/introspect) 无/过期/失效→401
  ┌─ 查 oauth2:access:a1b2c3d4... → 找到授权记录
  ├─ 检查 expiresAt 未过期
  ├─ 检查 status = active (未被 revoke)
  └─ 取出 sub/roles/scope → 构造 Authentication → 通过

// 4. 撤销 (强制下线/退出)
  POST /oauth2/revoke
  → SAS 标记 invalidated=true
  → RedisOAuth2AuthorizationService.save() 检测到 → remove() 删 key
  → 下次 introspect 查不到 → 立即 401

四、退出登录对接指南

完整退出需要两步操作组合：吊销 token + 销毁 session。单独执行任一步都无法实现真正退出。

步骤 端点 方法 作用
① 吊销 token /oauth2/revoke POST 标记 OAuth2Authorization invalidated → 删除 Redis 授权记录，资源服务器 introspect 查不到即拒绝
② 销毁 session /logout?post_logout_redirect_uri={url} GET 销毁 HttpSession → 302 回跳到指定地址

对接示例（客户端退出流程）：

// Step 1: 清理本地会话
sessionStorage.clear();

// Step 2: 吊销 token（RFC 7009）
// Authorization: Basic {base64(client_id:client_secret)}
POST /oauth2/revoke
Content-Type: application/x-www-form-urlencoded
Authorization: Basic d2ViLWFwcDoxMjM0NTY=

token=eyJraWQ...&token_type_hint=access_token
token=eyJraWQ...&token_type_hint=refresh_token

// Step 3: 销毁服务器 session
// 302 重定向到授权服务器
GET /logout?post_logout_redirect_uri=http://localhost:8300/
// 授权服务器销毁 session 后, 再 302 回 post_logout_redirect_uri 参数指定的地址

四种退出场景对比：

  • ① 客户端完整退出（推荐）
    清本地 → /oauth2/revoke 吊销 token → 跳 /logout 销毁 session。token 失效 + session 销毁，下次必须重新登录。
  • ② 仅吊销 token（/oauth2/revoke）
    删除 Redis 授权记录，但不销毁 HttpSession。客户端首页仍显示"已登录"，直到调 API 收 401 才发现 token 失效。
  • ③ 仅销毁 session（/logout）
    销毁 HttpSession，但旧 token 在过期前仍可调 API。适合换设备登录场景。
  • ④ 管理员强制下线
    服务端组合操作：SessionRegistry.expireNow() + 删除 Redis 授权记录。完整退出。
关键提醒：单独调 /oauth2/revoke 后，客户端刷新首页仍显示已登录 —— 因为客户端首页只查本地 session，不验证 token。 完整退出 = revoke token + logout session，缺一不可。
