## 三、风险项（功能验证时重点观察）

### R1 新旧栈无法同时运行（端口冲突，设计内但需知晓）
新栈 auth :9000 / access :9010 与旧栈相同；新 gateway :8080 与旧 portal-bff :8080 冲突。**验证时必须先停旧栈**。数据已用 v2 并行库 + Redis database 2（旧栈 db1）隔离，交替运行无数据串扰。

### R2 decide 链路的故障语义变化（本轮核心改造，需演练）
- 正常路径：登录 → auth 本地验密码 → decide 问询（30s SWR 缓存）→ 放行/拒绝
- **需演练**：停掉 access-service 后——①30s 内登录应正常（新鲜缓存）；②30s~10min 内登录应沿用最后真实判定（SWR stale）；③超 10min 应明确拒绝登录（fail-closed，不再有 user_label 猜测放行）
- 内省路径注意：access 的 `RbacAuthoritiesOpaqueTokenIntrospector` 对**有效用户令牌**每次内省都会经 decide 补角色（SWR 兜底）；client_credentials 令牌因 sys_user 查无此用户而短路，不触发 decide ✓

### R3 decide 的 clientId 上下文缺口（已闭合，建议评审确认）
`UserDetailsService.loadUserByUsername` 只有 username 无 clientId。处置：decide 支持 `clientId=null`（仅解析角色，供令牌 authorities 构建）；客户端准入闸门仍在 authorize/token 阶段由 `ClientUserPolicyService`（持有 clientId）执行。语义与旧版完全一致，但这是**设计上最值得二次确认的一点**。

### R4 policy.html 前端适配缺口
旧 `/api/admin/policies` 返回 ClientPolicyVO（含 clientName，**未配置策略的客户端也列出**）；新 `/api/admin/login-policies` 返回 ClientPolicy 实体列表（**仅已配置行，无 clientName**）。前端列表会变稀疏、名称列空。→ 功能验证阶段需小改 policy.html（从 `/api/admin/clients` 拉名录合并）。

### R5 删用户编排的补偿缺口
identity 编排第③步（access 清 RBAC）失败仅记日志，无重试/补偿任务——与旧版行为一致（旧版 auth 内同样 best-effort），但编排上移后此缺口更显眼。二期建议：失败标记 + 定时对账。

### R6 M2M 身份复用
identity-service 复用 `admin-m2m` 作为唯一机器身份（未新增 identity-m2m）。语义可接受（管理面机器身份），但 auth 内部 API 白名单与 access 管理 M2M 白名单共用同一身份，审计粒度较粗。→ 建议后续拆分。

## 四、与既定方案的偏差记录（均为有意识决策）

| 偏差 | 理由 |
|---|---|
| access 内部 rbac/asset/policy 分包未执行 | 纯外观改动；且 controller 叶包名（admin/portal）是 endpoint_policy 扫描播种的域名编码，贸然分包会破坏 resolveDomain 映射。保留为可选债务 |
| open-service 未引入 endpoint_policy 表机制 | 能力目录表 iam_api_capability 本身就是开放平台的准入登记表（登记制 + 路由匹配 + 订阅校验），再叠一层策略表是重复治理 |
| login-policies 控制器无 clientName 联查 | access 不直读认证中心 client 表（单一写者），名录合并交给前端 |
| CapabilityController 裁剪 roles/permissions 回显 | 三方无权感知平台内部权限模型（安全改进） |
| SWR 实现 = 同步刷新 + stale 兜底 | 非后台异步刷新；刷新请求承受一次远程延迟，换取无线程池的确定性语义 |
| decide 支持 clientId=null 模式 | 见 R3 |

## 五、功能验证建议顺序（确认本报告后执行）

1. **环境**：建三库（执行 sql/ 下脚本）→ 启动序：auth(9000) → access(9010) → open(9030) → identity(9020) → gateway(8080) → bff(8100/8101) → web(8200/8201) → demo(8300-8302)
2. **登录矩阵**：admin 登 admin-app ✓ / admin 登 portal-app ✗ / user 登 portal-app ✓ / user 登 admin-app ✗（验证 decide 全链路）
3. **SWR 演练**：登录成功后停 access → 30s 内再登录 ✓ → 10min 后登录 ✗（明确报错而非猜测放行）
4. **管理台全链路**：8201 登录 → 用户 CRUD（重点：删用户后权限中心角色绑定/应用授权被清理）→ 租户/会话/登录策略维护
5. **门户链路**：8200 SSO 登录 → 应用卡片 → RP-Initiated 登出
6. **开放链路**：web-demo(8300) 密码模式 → 经网关调能力；mobile-demo(8302) PKCE + 订阅准入；device-demo(8301) 设备码
7. **回归**：introspect/revoke/refresh、踢下线即时生效（portal 心跳）
